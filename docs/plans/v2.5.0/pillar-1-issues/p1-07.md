## Outcome and scope

- Provide selected-range totals and per-sender/per-command/unique-sender aggregates grouped by approved bot/channel dimensions.
- Reuse durable reply records where appropriate and add only the approved missing invocation evidence.
- Keep accepted usage, queued/sent replies, and outcomes distinguishable without changing command delivery behavior.
- Collect and durably retain individual interaction records for future browsing in v2.5.0; only the browsing interface is deferred. Reuse or extend existing reply records where sufficient, with a stable interaction reference and associated acceptance/context/outcome evidence.

## Settled requirements — 2026-10-07

- Count an eligible, deduplicated command as usage at acceptance time; count completed reply outcomes separately at resolution time. A retry or queue resumption must not create another invocation.
- Aggregate by original sender name, command, bot, and range, retaining applicable channel context. Ordinary channel messages do not provide a reliable sender public key; distinct names are not verified unique people/nodes and duplicate-name senders cannot currently be distinguished.
- Allow reliable sender identifiers and attribution evidence when genuinely available, without assigning advert/contact keys through name-only matching.
- Store individual acceptance timestamps, sender/bot/channel/command context, packet references, and associated reply lifecycle fields for later reporting. Keep collection independent of dashboard enablement. Migration 9 and completion-time row retention were approved on 2026-10-08 and implemented below.
- Retain bot interaction history for the same runtime-configurable duration as other key historical metrics, using shared metrics retention configuration. Do not introduce a separate bot-history duration. Preserve the existing unlimited default unless separately agreed, and protect pending replies from history pruning.
- See `docs/plans/v2.5.0/pillar-1-decisions.md` for worked examples and primary-source evidence, under the owning decision issue #23.

### 1. Feature Summary

Report accepted, deduplicated bot commands independently of reply outcomes, grouped by original sender name, command, bot, channel, and reporting range. Keep individual backend records available for future browsing without introducing a browsing API or UI now.

### 2. Relevant Existing Architecture

- `src/bots/channel-bot.js`: `#handleRawPacket` decrypts, matches commands, checks minimum hops, and filters duplicates before `ReplyQueue.enqueue`. Its context already includes bot, channel, trigger, sender, packet hash, and validated handler state.
- `src/bots/reply-queue.js`: `enqueue` stamps Observer time and persists a pending item; restart resumes the same row. Completion, expiry, and failure update that row. Shutdown preserves pending work.
- `src/metrics/store.js`: migrations currently end at version 8. `bot_replies` has a durable integer `id`, nullable legacy acceptance/sender fields, context, status, resolution time, and queue duration. `queryBotCommandCounts` and `queryBotCommandCountsByBot` count sent replies by resolution time. `pruneOlderThan` deletes only completed rows by `resolved_at < cutoff`.
- `src/metrics/stats-reporter.js` and the dashboard consume existing delivery-oriented reads. Preserve their behavior in this issue; #35/#36 own new presentation/API integration.
- Existing coverage lives in `test/metrics/store.test.js`, `test/bots/channel-bot.test.js`, and `test/bots/reply-queue.test.js`.

### 3. Proposed Approach

Reuse `bot_replies` as the interaction record. Its durable `id` is the stable reference within this Observer database; do not create a duplicate interaction table or rewrite matching/dispatch. Use non-null `enqueued_at` as acceptance evidence for records whose provenance supports that meaning. Successful durable enqueue is the proposed acceptance commit point; stopped/rejected enqueues are not accepted work. A persistence failure remains visible rather than producing an invented successful record.

Add narrowly named store reads for accepted usage and sender totals, leaving existing sent-reply methods unchanged. Use half-open epoch-millisecond ranges `[start, end)` against `enqueued_at` for usage and `resolved_at` for outcomes. Group sender names with exact/BINARY comparison; never trim, lowercase, or attach a public key through a name match. Unknown legacy sender data is a separate unavailable category, excluded from the distinct-known-name count.

Propose nullable `sender_identifier`, `sender_identifier_kind`, and `sender_identifier_source` columns for future reliable attribution. Central strict AJV schemas define all-null or complete validated evidence; current channel messages always leave them null. No speculative attribution producer is introduced. Preserve original sender text and existing validated handler context; do not add message bodies, reply bodies, or additional command arguments.

Propose preserving the existing completion-time retention cutoff for the whole interaction row. Pending rows remain protected; a retained recent completion can carry an acceptance timestamp older than the configured duration. Document that behavior explicitly. Add an accepted-time index appropriate to bot/range aggregates; measure grouping queries before adding further indexes. No schema version number is reserved until implementation order is fixed.

### 6. Risks and Edge Cases

- Current duplicate filtering is bot-local transient bookkeeping; database persistence does not imply all historical RF redeliveries are deduplicated forever. T1 must confirm the scope expected across restart without silently changing bot delivery policy.
- A send can succeed before its durable resolution write fails; preserve the existing observable recovery limitation rather than adding an unrelated exactly-once send system.
- Original sender names can collide; optional evidence fields do not solve identity when the protocol supplies none.
- Existing historical rows may have incomplete context. Never infer acceptance from completion or sender identity from nearby adverts.
- Unlimited retention remains the agreed existing default; grouping/index cost must be assessed using retained data.

#### Backend read contract

All ranges are half-open epoch milliseconds `[start, end)`; callers can supply preset-derived or custom bounds. Range DTOs accept optional exact `botName`, `channel`, `trigger`, `sender` filters. Group DTOs add `limit` (default 100, maximum 200) and `offset` (default 0). Invalid bounds/types/additional properties are rejected; equal bounds return an empty range.

| Method | Result / timestamp |
| --- | --- |
| `queryBotUsageTotals` | `{accepted, distinctSenderNames, unknownSenderAccepted, retainedUnknownAcceptance, earliestAcceptanceAt}`; counts use `enqueued_at`. Last two fields describe retained coverage under the same filters, independent of the requested range. |
| `queryBotUsageGroups` | `{total, groups:[{botName, channel, trigger, sender, count}]}`; `total` is group count before pagination. Acceptance time. |
| `queryBotSenderCounts` | `{total, senders:[{sender, count}]}`; null is unavailable name evidence, excluded from distinct-known-name totals. Acceptance time. |
| `queryBotOutcomeGroups` | `{total, groups:[{botName, channel, trigger, sender, outcome, count}]}`; resolution time, terminal statuses only. |
| `getEarliestBotAcceptanceAt` | Minimum retained known acceptance under optional exact filters, or null; independent of packet samples. |

Pre-v5 completed events lacking `enqueued_at` remain unavailable; retained migrated pending/completed interactions with original durable enqueue evidence contribute normally. Coverage metadata does not imply continuous historical completeness. The new ID guarantee applies from migration 9 onward; pruned pre-upgrade records cannot be reconstructed. Original names remain labels, even when optional identifier evidence exists.
