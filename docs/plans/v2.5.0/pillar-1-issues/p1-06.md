- Learn paths from ordinary observed traffic without transmitting discovery traffic or storing raw packets locally.
- Persist multiple observations/relationships with hop distance, frequency, first/last observation, and approved freshness/retention semantics.
- Resolve compact repeater identifiers conservatively against full known identities; expose reusable evidence for telemetry and future bot consumers.

### 1. Feature Summary

Persist compact path evidence from traffic already received, distinguish traveled flood paths from remaining direct paths, and expose conservative observed-proximity candidates for later telemetry consumers. Keep multiple routes, timing and reception frequency, even while identity is unknown or colliding. Do not fabricate a trusted network graph or an outbound route.

### 2. Codebase and Protocol Findings

- Runtime baseline: user-pushed a903e0e, installed @liamcottle/meshcore.js 1.15.0 and MetricsStore migration 12. Current documentation HEAD is 217bbc4; release planning records are tracked there. Node >=22.13.0 / node:sqlite, ESM JavaScript, centralized strict AJV/configuration and structured logging remain required. The user's `.gitignore` work is not modified by this task.
- `src/packets/packet-normalizer.js` stamps Observer reception time and validates normalized input. `packet-decoder.js` emits the existing flat MQTT compatibility DTO; it does not expose path metadata. `packet-pipeline.js` intentionally emits every reception, including duplicate/re-heard traffic. A separate consumer can parse `raw` without changing this public shape or bot duplicate handling.
- Installed `Packet.fromBytes`, `getPathHashSize`, `getPathHashCount`, `getPathHashes` and MeshCorePath already support 1/2/3-byte entries. `BufferReader.readBytes` can return fewer bytes than requested, so successful library construction alone is insufficient structural validation. The library's `isRouteFlood()` checks only unscoped FLOOD; explicitly classify both flood route enums.
- Firmware reference: meshcore-dev/MeshCore a366955cb2f67b8e6842d4f00d2b6a554dddd88a, committed 2026-09-30. Mesh::routeRecvPacket appends relay prefixes to flood paths; direct forwarding removes the next prefix, while TRACE uses the header path for SNR data. Therefore flood order is earliest relay to latest relay, direct header paths are remaining forwarding instructions, and TRACE entries are not normal repeater identifiers. See the [scoped protocol notes](../topology-protocol-notes.md).
- Pinned Identity::copyHashTo copies the leading public-key bytes. A unique local inventory match is a prefix association, not cryptographic proof of that relay. Missing/unknown nodes elsewhere can collide with the same prefix; even a verified advert signature does not authenticate a mutable relay path.
- Pinned firmware limits: 1/2/3-byte hash widths, encoded count 0–63, path bytes <=64 and payload <=184, with payload version 0 denoting the supported v1 format. Width 4 is reserved. For 2/3-byte paths, effective maxima are 32/21 entries. Deployed firmware versions and actual RF reachability remain unknown; this passive feature needs no library upgrade or real-radio probe.
- `NodeRegistry.findByPrefix` currently returns a preferred node alongside ambiguous matches for display. Do not reuse that preferred node as a topology target. Resolve against every known full-key node before checking the unique match's REPEATER type; filtering by type first could hide collisions.
- MetricsStore owns migrations, parameterized reads/writes and shared retention. `src/index.js` owns packet listeners and shutdown; MetricsSampler owns the configurable always-on cadence and daily maintenance. #24/#25 supply active run identities and parent-retention protection. Reuse these seams.

### 3. Concrete Proposed Contract

#### 3.1 Parsing and evidence classification

Add `src/nodes/topology-schemas.js`, `topology-parser.js` and a small `TopologyObserver`. Use the installed Packet decoder only. Validate a bounded local frame view with AJV before parsing, check binary boundaries/encoded sizes, then validate the derived strict DTO before storage/business logic. No second decoder or manual substitute for DTO schemas.

Accept supported v1 normal header paths from FLOOD/TRANSPORT_FLOOD as `flood-traversed` and DIRECT/TRANSPORT_DIRECT as `direct-remaining`. Explicitly exclude TRACE, reserved payload types 12–14, reserved width 4, unsupported payload versions, truncation, oversized paths/payloads and invalid observer identity/time. Treat an empty path as no relay evidence: it cannot assign a sender identity or distance; existing verified zero-hop advert evidence remains owned by #26. Parse header path only, never decrypted PATH-return contents, group-message bodies or telemetry credentials.

Derived DTO: active run UUID, uppercase 32-byte Observer public key, original reception epoch milliseconds, route enum, evidence kind, payload version, hash width, ordered uppercase fixed-width prefixes, nullable transport-code pair, and `containsRepeatedPrefix`. The schema enforces exact prefix width, supported count/byte bounds and conditional route/transport fields. Do not store raw frames, payloads, packet hashes, sender/message text, SNR or RSSI in this feature.

For a flood path with n entries, prefix at zero-based position i has observed distance n-i. `AC01 -> 9905 -> E85C -> Observer` yields 3/2/1. Direct-remaining paths retain their order and frequency for diagnostics, but their observed distance is null and they cannot provide proximity candidates. Repeated prefixes are preserved by position, labeled loop-or-collision evidence, and excluded from automatic proximity candidate selection.

#### 3.2 Identity, frequency and freshness

Resolve prefixes dynamically at read time against the current full-key inventory. Outcomes are `unresolved`, `unique` or `ambiguous`, with bounded candidate identity pages; ambiguous evidence has no selected full key. A unique association is eligible for the observed-proximity query only when its current stored type is REPEATER. No inferred node is added to trusted inventory, and a later advert/collision changes association without rewriting the observed path.

Scope every path to the observing radio's full public key, route/evidence kind, width, transport codes and ordered prefix sequence. A deterministic SHA-256 identifier over a versioned canonical representation distinguishes routes/context; on an existing digest, verify canonical fields match before combining records. Observer replacement must not inherit another radio's proximity. A closed database copy retains its original evidence identity/context, not a claim of a new physical observation.

One successfully persisted qualifying PacketPipeline reception increments route frequency once, including repeated physical copies. This is reception frequency, not distinct messages, verified sources or independent route successes. Prefix occurrences are positional; repeated entries do not multiply the route count. Record first=min and last=max reception times; out-of-order work cannot regress recency. Preserve original receivedAt through restart; a restart never refreshes a route.

Propose `PACKETCAPTURE_TOPOLOGY_FRESHNESS_HOURS=72`, whole 1–8760 override, matching example/code fallback. This is a separate observed-path policy, not #26's direct-advert eligibility. Freshness expires at equality. Evidence later than query `now` is conservatively ineligible; clock rollback cannot renew it. Save stale evidence for browsing rather than deleting it on expiry.

The candidate query accepts explicit radius 0–63, current time and freshness window; radius 0 produces no flood-relay candidates. Exclude the observing radio's exact full key as a remote target. Return the freshest eligible evidence per observed distance plus at most three alternate path references per candidate; candidate pages cap at 200. Order recommendations by shorter distance, newer observation, higher observed reception count and stable ID. A newer outside-radius route does not erase an older inside-radius route while that older route remains fresh; report both. Labels must say `observedProximityCandidate`/`outboundRouteVerified: false`, not reachable or guaranteed telemetry eligibility. #34 must recheck time, radius, target ambiguity, routing/contact prerequisites and failure/backoff policy immediately before dispatch; #27 sends nothing and does not reverse a path into a command route.

#### 3.3 Storage and bounded collection

Propose migration 13, allocated only after approval and rechecking the current migration baseline:

| Table | Purpose / key / retained fields |
| --- | --- |
| topology_paths | Stable AUTOINCREMENT identity plus unique canonical digest; Observer public key, route/kind/width/transport context, compact ordered path hex, repeated-prefix flag, successful reception count, original first/last times. No run FK on the indefinite summary. |
| topology_path_hops | FK to path, positional key `(path_id, position)`, prefix bytes and nullable flood distance; indexed `(hash_width, prefix)` association lookup. At most 63 rows per distinct path, not per reception. |
| topology_observations | Stable AUTOINCREMENT ID, FK to path and run, reception time; one compact successful reception record. Time and path/time/run indexes support exact `[start,end)` counts without storing a frame or message. |
| topology_capture_samples | Run-linked sampled coverage: Observer identity, observation time and accepted/suppressed/failed/malformed/unsupported/no-relay counts since the last successful coverage flush. Valid empty paths have a separate no-relay count; they are not malformed/unsupported. No raw error data. |

Insert/upsert path, first-time positional hops and reception detail in one transaction. Any failure rolls back all of that reception's state. Run/Observer context is validated before mutation; detail/coverage must refer to the active owned run. Frequency and detail cannot disagree due to a partially committed reception. No fabricated historical rows on upgrade.

Include three fixed expression indexes on normalized inventory prefixes (`upper(substr(public_key_hex,1,2/4/6))`) for 1/2/3-byte associations, preserving existing key values while matching legacy letter case conservatively. Validate the supported width before selecting one of three fixed parameterized query shapes. Count all identities before type eligibility; batch distinct prefix resolution where needed and verify the planner uses the indexes. Duplicate/invalid legacy identity evidence must not create a selected target. Avoid a per-route full inventory scan or an uncapped nested identity expansion. This adds indexes, not an extra identity registry or inferred nodes.

Propose `PACKETCAPTURE_TOPOLOGY_MAX_OBSERVATIONS_PER_MINUTE=600`, whole 1–6000 override, matching example/code fallback. Enforce a rolling monotonic minute of write attempts, including failed attempts, before any persistent mutation; use a bounded timestamp queue. Suppressed receptions do not advance route recency/count or manufacture proximity. Failure/throttling/invalid/unsupported/valid-no-relay counts remain separate; flush them on the existing sampler cadence, acknowledge only after a successful coverage write, and flush once after listener detachment at orderly shutdown. Abrupt death/failed final writes can lose unpersisted coverage counts, so totals remain observed lower bounds. Collector failures must never interrupt capture, MQTT, bot processing or ordinary sampler persistence.

This bounds write rate, per-path size/fan-out and result sizes. It does **not** promise a permanent disk ceiling under unlimited retention. Changing the write cap trades retained topology completeness for local write load and must be documented. No growing queue of raw packets, new high-frequency timer or new database is proposed.

#### 3.4 Retention and reads

Historical reception detail and coverage follow existing `PACKETCAPTURE_METRICS_UI_RETENTION_DAYS`, default 0/unlimited. Delete these children before existing run-parent pruning. Path summaries/positions survive detail pruning by default, preserving learned routes, original first/last time and successful reception frequency; mark summary totals as cumulative persisted evidence, never reconstruct selected-range counts from first/last timestamps.

Propose `PACKETCAPTURE_TOPOLOGY_PRUNE_AFTER_DAYS=0`, whole 0–36500 override: opt-in daily maintenance may delete paths whose last successful reception is at least N days old **only after no retained detail references them**. Remove positional children and parent atomically. Preserve inventory, verified advert/direct evidence, still-referenced paths, and unrelated datasets. Returning a deliberately purged route starts new local route history; it must not create a new node/discovery. Cleanup reuses SQLite pages rather than silently VACUUMing. With unlimited detail retention, catalog pruning normally removes nothing.

Provide strict, parameterized internal APIs: capped path/observation pages (max 200), a single-path positional view (max 63), capped exact prefix association pages (max 200), paged retained-range route counts (max 200) and bounded observed-proximity pages/alternate routes. Path-list rows carry compact metadata, not nested lists of every matching identity; a single-path view supplies resolution status/count and the unique identity only, with a separate paged ambiguity lookup. Current summary versus retained `[start,end)` detail must be explicit. Include retention/coverage/freshness/ambiguity flags; return missing data as unknown, not zero distance. Use indexed queries and avoid loading all inventory/routes into JavaScript. Public endpoints/UI, active route use, telemetry polls and future bot consumers remain their owning issues (#35/#36/#34 and Pillar 3).
