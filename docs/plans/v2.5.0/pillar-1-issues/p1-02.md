## Settled bot-reporting decisions — 2026-10-07

- Usage is an eligible command accepted after duplicate filtering; duplicate copies do not increase usage. Count usage at acceptance time and each completed reply outcome at resolution time.
- Report successful replies and other outcomes separately from usage. Legacy missing sender/acceptance evidence remains unavailable rather than inferred.
- Use distinct original sender names unless reliable message-to-sender identity evidence is available. Ordinary channel messages provide no reliable sender public key; duplicate names remain ambiguous and name-only contact/advert matches must not be used as attribution.
- v2.5.0 includes aggregates by sender, command, bot, and range **and durable individual interaction records for later browsing**. Only the browsing interface is deferred. Reuse/extend existing MetricsStore reply records where appropriate rather than assuming duplicate storage is needed.
- Backend planning must retain acceptance, command/bot/channel/sender context and associated outcomes/timestamps with a stable interaction reference, allowing optional reliable identity evidence. Raw packet archiving is excluded; additional message content is not implicitly required.
- Bot interaction history follows the same runtime-configurable retention duration as other key historical metrics, using the shared metrics retention setting rather than an independent bot-history duration. Preserve the existing unlimited default unless separately changed; pending replies must not be pruned as history.
- Concrete #28 cutoff/schema decisions were approved on 2026-10-08: successful durable enqueue is acceptance; migration 9 reuses stable non-recycled database-local IDs and adds optional identifier/kind/source evidence; whole completed rows retain the existing completion-time cutoff, protecting pending work. Existing transient bot-local duplicate filtering is preserved, with no permanent RF deduplication claim across restart. Backend aggregate reads are implemented; public sender exposure remains #35. Other P1 decisions remain unresolved, so this issue stays open.

Full local decision record and primary-source evidence: `docs/plans/v2.5.0/pillar-1-decisions.md`.

## Settled node-advert decisions — 2026-10-07

- Report distinct advert events and distinct full-public-key nodes separately, beginning with Companion and Repeater nodes.
- Count the same signed advert once despite relayed copies; retain useful reception/path/direct-heard evidence separately. Fresh distinct adverts from a known node count as re-hears, without collapsing all activity to one event per sample.
- Include verified unnamed nodes by public key with an explicit `Unnamed` display fallback. Malformed/unverified adverts cannot enter trusted reporting or direct-discovery eligibility.
- A rename does not create a new full-key identity. Existing first/last-heard inventory is not complete historical advert evidence; unavailable legacy events must not be fabricated.
- Node retention settled on 2026-10-08: historical advert events use shared runtime-configurable metrics retention; full-key inventory with known name/type and first/last-heard data survives event pruning. A returning known key remains a re-hear. Inventory does not establish current reachability or reconstruct pruned historical events.
- Direct-heard policy settled on 2026-10-08: runtime-configurable reception-time eligibility, refreshed only by verified zero-hop repeater adverts. Expiry pauses new region queries, preserving inventory and previous successful answers. Advert cadence varies; operator guidance is one-hour local and 47-hour flood adverts, without assuming every deployment follows it.
- Direct-heard default settled on 2026-10-08: 72 hours, with a validated operator override and the same default in example configuration and central code for omitted values. Exact validation bounds and concrete schema/migration/cutoff design remain implementation-plan details. See #26/#31.
- Configuration direction applies across applicable release settings: valid operator overrides take precedence; approved optional defaults are documented with units in examples and implemented in central configuration code. Invalid explicit values fail before side effects. Required values/secrets do not gain fabricated defaults. Setup/doctor/startup share the interpretation, with example/code agreement checked during implementation validation; see #68/#74.

- Concrete #26 contracts approved and implemented on 2026-10-08: full SHA-256 signed-payload fingerprint, actual nullable names/type snapshots, reception time captured before asynchronous verification, configured 72-hour default with whole-hour 1–8760 overrides, expiry at equality and conservative future/rollback/restart eligibility. Migration 10 follows #28's committed migration 9; range/type/full-key reads remain internal for #35/#36 presentation.
- Retention direction finalized on 2026-10-08: the user delegates best judgment with offline operation, save first/purge later and enterprise reliability priorities. Preserve inventory, known names/types, first/last-heard and direct evidence indefinitely. `PACKETCAPTURE_REPEATER_FINGERPRINT_PRUNE_AFTER_DAYS=0` defaults off; whole-day 0–36500 overrides select inactive repeaters, including duplicates as activity. Local daily cleanup removes only fingerprints whose event detail has already expired, protecting retained events and the original discovery fingerprint. Returning known keys remain known; already-pruned non-discovery payloads may count as re-hears again after opt-in cleanup. Shared history retention stays separate. #26's complete acceptance is validated; no question remains for this feature.
- Validation: 51 files / 544 tests pass, CI coverage thresholds and lint pass; genuine signatures, asynchronous ordering, upgrade/rollback/reopen, shared retention, separate duplicate/direct evidence, strict prune settings/cutoffs, protected atomic cleanup, failure isolation and real-store offline maintenance are covered. A 20,000-entry digest ledger used about 43 bytes per fingerprint in SQLite pages; no raw frames or message bodies are stored in it.
- Release-wide direction: core local observation and insight must remain useful without internet; optional cloud forwarding cannot gate local persistence or reads. Preserve learned information by default, make purges explicit, test migrations/recovery/failures and label stale/unknown data truthfully. This is a design/validation constraint, not a claim of formal enterprise certification. Existing chart CDN dependency is recorded in #42/#83; #37 captures integrated offline/backend recovery validation. These queued features are not implemented or marked In progress merely by recording the requirement.

## Settled run-history decisions — 2026-10-08

- User direction "Pushed to the release-v_2_5_0 branch. Clear to proceed" approves the next #24 implementation after #26, carrying the prior offline/save-first delegated judgment.
- Generate one database-local instance UUID with the first persisted run, and one UUID per startup. Capture bootstrap wall/monotonic clocks at main entry; persist only after config/store succeeds and before hardware/network. No host/PID/secret inventory or fabricated legacy sessions; copying the closed database copies its history/identity.
- Enforce one Observer through exclusive SQLite connection ownership before recovery. OS releases ownership after death; no lease, sidecar or online coordination. Dashboard reads use the same store; external SQLite tools require stopping the Observer first.
- Checkpoint at the existing configurable sampler cadence. Monotonic elapsed time measures runtime; wall time labels observations and discontinuities/backward time are flagged. Failed checkpoints preserve prior evidence without stopping sampling.
- Mark prior unclosed runs unclean at restart with null end/reason and the last persisted observed-duration lower bound. Never count downtime or invent exact crash time. Clean end requires successful bounded teardown and pending advert drain before store close; repeated signals cannot double-count. Failures/timeouts do not claim clean completion.
- Cumulative runtime always means retained observed evidence, with state counts, lower-bound/clock flags and earliest retained start. Pages select bootstrap starts in `[start,end)`, max 200, without wall-range proration. Shared history retention defaults unlimited; clean cutoff is end, recovered unclean cutoff last known alive. Protect running and FK-referenced parents and retain instance identity.
- Migration 11 follows pushed advert migration 10. All 564 tests, CI coverage and lint pass, including real-process offline heartbeat/teardown, concurrent-start rejection, abrupt death/recovery and advert-drain fixtures. #25 owns resource/events; #35/#36 own public reporting/presentation. This settles the run family without closing this umbrella issue.

## Settled resource/event decisions — 2026-10-08

- The user approves the next #25 task after pushing #24; delegated offline/save-first judgment resolves the concrete measurement/event/storage/configuration choices in #25's finalized plan.
- Reuse the configurable always-on sampler cadence: default 10 seconds, minimum 1 second. One-logical-CPU percentages use raw user/system microseconds divided by actual monotonic elapsed time and may exceed 100%; no host/quota inference. RSS/heap total/heap used/external memory are byte gauges. First/reset/unavailable utilization is null, distinct from true zero.
- Include built-in ELU active/idle milliseconds and 0–1 utilization after deterministic tests and local overhead verification; distinguish it from CPU and event-loop delay. No histogram, extra timer or dependency.
- Migration 12 stores run-linked resource samples and typed radio.connected/disconnected/connect-error, broker.state and bot.readiness events. Sample/heartbeat commit atomically, optional failures remain nonfatal to capture and fall back to ordinary checkpoints. Never retain radio error text, credentials, messages or configuration dumps.
- Radio timestamps are hook-observation times; broker/bot transitions use consecutive snapshots with actual monotonic observation windows. First snapshots establish baseline; stable states do not repeat and between-sample flaps may be missed.
- `PACKETCAPTURE_RUNTIME_EVENT_MAX_PER_MINUTE=60`, whole 1–600 override, caps attempts in a sliding monotonic minute. Failed writes consume budget. Suppressed/failed counts are acknowledged only after successful process persistence and flushed after collector detachment at orderly shutdown; unpersisted abrupt/final-failure counts remain unavailable.
- Shared unlimited-by-default day-based retention prunes children first and protects referenced/active run parents. Internal raw pages cap at 200, history at 1000 buckets; weighted CPU/ELU, per-gauge observation counts, no filled gaps, explicit mixed-run buckets and optional run filters. Public reporting/UI remains #35/#36.
- All 57 files / 591 tests, CI coverage thresholds and lint pass. On this Windows / Node v24.21.0 workspace, normal collection/write p95 is 3.781ms with 20,500 retained samples, below the 10ms local target. #37 still owns integrated soak/RF/offline release validation. This settles the resource family without closing the unrelated decision work in #23.
