### 3. Approved Approach

#### TELEMETRY-PLAN-01 — Typed source and observation semantics

Introduce centralized strict schemas for raw decoder inputs, normalized observations/results, configuration and reads. Validate through shared AJV before decoding or persistence; reject unknown fields including password/token/session/credential objects. Follow shape validation with narrow byte-count, cross-field identity/time and payload-size invariants.

`recordTelemetryResult` receives one terminal **request**, not an invented atomic multi-request poll: UUID request/run, full uppercase reporter and target keys, component (`status`, `sensors`, `neighbours`), validated original operation parameters, captured dispatch/terminal time, nullable reply receipt time, route, anomaly flag, fixed outcome/reason, decoder version, and optional normalized observation. No credential value/reference, private key, login reply, raw error string or caller-provided SQL is accepted. Successful/partial reply observation time is captured receipt time; local completion and any remote relative time remain separate. Request tag/provenance is correlation evidence from the trusted Companion, not independently authenticated repeater identity.

Fixed terminal states distinguish `answered`, `partial`, `failed`, and `unsupported`. A validated failed/unsupported attempt carries no observation, never inserts an empty snapshot and never replaces latest useful data. Structurally malformed/truncated known fields yield failure without an accepted prefix sample. A safe known prefix followed by an unsupported layout/type may become a clearly partial observation; it cannot certify complete decoding or an empty complete result. Observation records always describe **one returned response**, not complete hardware/mesh inventory.

Keep decoded raw numeric values alongside scaled values where fractional scaling occurs, so signedness/scales can be audited. Do not compute battery percentage, battery health, remaining lifetime, aggregate radio utilisation or counter rates. Zero stays zero; unavailable fields are null or absent from a typed reading list, with reason/coverage metadata. Counters may wrap/reboot; each observation is a gauge/counter snapshot without cross-run delta inference.

#### TELEMETRY-PLAN-02 — Supported decoders and conservative completeness

**Status:** support the reviewed common 48-byte prefix and the current 56-byte source layout. Input explicitly identifies the reviewed interpretation profile (`common48` or `current56`), plus whether profile evidence is established or unknown. The default/unknown path reads only the common prefix and reports extension fields unavailable with prefix-only quality; byte length or zero trailing bytes must never select the 56-byte interpretation. #34 must establish any deployed profile evidence before opting into extension decoding. Profile metadata records an interpretation assumption, not a newly inferred firmware version.

| Supported status field | Wire interpretation / normalized meaning |
| --- | --- |
| `batteryMillivolts`, `txQueueLength` | u16 LE at 0/2; millivolts and queued items, no battery percentage |
| `noiseFloorDbm`, `lastRssiDbm` | s16 LE at 4/6; preserve measured values |
| `packetsReceived`, `packetsSent` | u32 LE at 8/12; cumulative counters |
| `txAirtimeSeconds`, `uptimeSeconds` | u32 LE at 16/20; seconds |
| `sentFlood`, `sentDirect`, `receivedFlood`, `receivedDirect` | u32 LE at 24/28/32/36; counters |
| `errorEventFlags` | u16 LE at 40; bit flags, not an event count |
| `lastSnrQuarterDb`, `lastSnrDb` | s16 LE at 42; retain raw and divide by 4 |
| `directDuplicates`, `floodDuplicates` | u16 LE at 44/46; counters |
| `rxAirtimeSeconds`, `receiveErrors` | u32 LE at 48/52 **only with established current56 interpretation**; otherwise null |

Known-profile parsing reads every structural field before evaluating a bounded all-zero padding suffix of at most 15 bytes. Unknown-profile parsing is explicitly prefix-only within the reviewed 48–71-byte envelope; it does not interpret the unresolved suffix. Reject shorter/over-bound/unsupported envelopes. Never strip arbitrary trailing zeros before decoding fixed status fields. Crypto and path-return framing can change exposed padding length; do not require a universal modulo-16 length on the host body.

**Sensors:** initial whitelist is LPP voltage 116, current 117, temperature 103, relative humidity 104, and barometric pressure 115. Preserve source channel/type/order/occurrence, raw value, scale/unit and decoded value. Voltage/current are signed s16 BE at 0.01 V / 0.001 A **for the pinned actual encoder**, temperature s16 BE at 0.1°C, humidity u8 at 0.5%, pressure u16 BE at 0.1 hPa. Values use wire ranges; do not reject a measured negative or unusual value solely through a guessed board calibration. A channel does not prove ambient/MCU/battery association; channel 1 is self in the pinned emitter, without assigning every channel-1 value a board-health meaning.

Use a small response-specific, width-checked JavaScript normalizer over the already correlated body; no decoding library/dependency is added and installed files remain untouched. Bound bytes at 170 and readings at 56 (the minimum whitelisted encoded record is three bytes). Parse only complete known fields. Unknown type with unknown width stops safely and preserves preceding supported readings as partial, with fixed type/offset/remaining-count evidence, never arbitrary remainder content. Recognized excluded types may be skipped only using a reviewed fixed width and bounds; unexpected GPS values are neither decoded into stored location nor logged. An all-zero suffix of at most 15 bytes is padding only at a record boundary in the reviewed positive-channel emitter profile; do not trim zeros from legitimate zero-valued readings. Channel-zero/ambiguous profiles are unsupported/partial rather than silently interpreted as a zero sensor. A proven valid empty response remains distinct from an unsupported-only, malformed or missing response. `decoded` means the permitted returned payload was interpreted; it never means every physical sensor was measured or that the firmware's LPP buffer could not omit fields.

**Neighbours:** parse reviewed request version 0 with the exact captured `count`, `offset`, `orderBy`, and `prefixLength`. Header total/result counts are u16 LE; each record has exactly the requested prefix bytes, u32 LE heard-seconds-ago and s8 quarter-dB SNR. Bound result count by requested count and actual body/entry width (host maximum 27 at one-byte prefixes). Validate count relationships and expected entry bytes before reading; accept only a remaining bounded zero padding suffix. Preserve page order, parameters, reported total, received count and prefix length. The pinned emitter's 130-byte entry budget is fixture evidence, not a universal board capacity.

Every prefix remains a **remote-reported identity observation**, including a full 32-byte value; do not upsert verified inventory, assert reachability, infer hop radius or join it silently to a unique registry node. Preserve uint32 relative age verbatim without creating a host last-heard timestamp or assuming the repeater clock is healthy. A zero-result page at a nonzero offset is not an empty whole neighbour table. Pages can shift during collection; no complete/atomic stitched neighbour list is created in #33.

#### TELEMETRY-PLAN-03 — Single-store history/latest ownership

Propose migration **16**, allocated only when approved T3 begins and rechecked against the actual migration head. Add three owned tables:

| Table | Responsibility |
| --- | --- |
| `telemetry_query_outcomes` | One immutable terminal request, active/source run FK, reporter/target/component/validated request-variant/time/route/anomaly/outcome/fixed reason |
| `telemetry_observations` | One accepted decoded/partial observation per answered request, original receipt time, versioned strict bounded normalized JSON, byte/field quality metadata and conflict evidence; FK to its owning outcome/full-key scope |
| `telemetry_latest` | Per reporter/target/component/request variant pointers to latest useful observation and, separately, latest fully decoded observation; neither pointer claims complete remote inventory |

Use CHECK/FK/index constraints and atomic writes for outcome, observation and latest-pointer updates. Canonical validated request variants are internal: status interpretation profile, sensors' requested permission mask, neighbours' version/count/offset/order/prefix width. Latest reads require the appropriate parameters rather than combining unlike permission selections or page offsets into one apparently complete snapshot. Range history can explicitly include all variants with each result's parameters visible. Clock-anomalous/impossible receipt ordering remains saved history/outcome evidence and does not advance useful or fully decoded pointers; a latest saved observation can still become future-dated after a later clock rollback, which reads must disclose. Equal-time ambiguity remains explicitly flagged rather than certified as fresh.

No decoded observation is reconstructed from existing node inventory, region declarations, old logs or remote counters. Same request replay with identical content is idempotent; changed immutable content under that request is rejected. Distinct requests colliding at the same reporter/target/component/variant/receipt time retain evidence, mark ambiguity and do not certify a uniquely ordered current state. Order latest by original receipt time with deterministic tie metadata, never arrival/commit time. Partial observations may update the explicitly partial latest-useful pointer; retain the older latest-fully-decoded pointer separately without merging old fields into a fresh observation. Failure and unsupported results leave both pointers untouched. Require active owned run for writes; reopening alone grants no mutation authority.

Persist supported normalized fields and bounded diagnostic metadata only. No raw RF packet, opaque encrypted/decrypted response archive, credential-bearing authentication record or personal location is introduced. Raw packet persistence remains MQTT's existing responsibility. Bound each canonical normalized result to 16 KiB with a centralized semantic byte check after AJV, before any transaction. Known values absent in a later reply are not silently copied forward as current. Saved learned observations stay usable offline and independently of brokers/UI/polling activation.

#### TELEMETRY-PLAN-04 — Queries, freshness and save-first retention

Add internal store seams `getTelemetryLatest`, `queryTelemetryObservations`, and `queryTelemetryOutcomes`; no HTTP endpoint or UI change. Require validated full-key/component/variant scope for latest, explicit `now` and freshness window; history uses explicit millisecond `[start,end)` ranges, optional typed scope/outcome filters, default 100/max 200 rows and bounded offset. Use fixed parameterized SQL and indexes on receipt/completion time, reporter/target/component/variant and run. Select headers/pages before JSON mapping; no unbounded body hydration, page aggregation or dynamic column/filter text.

Latest returns observation/provenance plus explicit `unknown`, `fresh`, `stale`, `future`, `clock-anomaly`, or `ambiguous` state; decode quality/response-only coverage is separate from age. Include latest outcome and optional older fully-decoded observation with its own original time/freshness. Failed polls can coexist with previously useful stale data. No fabricated zero totals or fresh timestamp is substituted for an empty range or unavailable measurement. History counts/earliest/latest describe retained evidence, not a guaranteed full lifetime or time-weighted average. Preserve rollback/restart conservatism using durable run time and a read high-water mark, as existing region reads do.

Propose `PACKETCAPTURE_TELEMETRY_FRESHNESS_HOURS=72`, whole hours 1–8760, with the same omitted-value default in central code and `.env.example`; invalid explicit values fail startup before side effects. All components share this observation-age policy initially, with independently supplied per-observation times. It does not grant RF eligibility, change poll cadence, create pruning or refresh a saved measurement. Future #34 polling has its own configuration/approval.

Historical retention follows existing `PACKETCAPTURE_METRICS_UI_RETENTION_DAYS` (0/unlimited), regardless of UI. Protect both latest pointers and required source runs even when stale, old or legitimately empty. Child-first shared pruning removes only unreferenced historical observations/outcomes strictly older than the cutoff on their original receipt **and** terminal times; equality stays. Do not purge latest/inventory on an unavailable response or stale clock. Pruning reports retained coverage honestly. No new cleanup loop, outbox, schedule table, hot reload or feature-specific retention override is added.

#### TELEMETRY-PLAN-05 — Evidence, rollout and boundaries

Use deterministic source-grounded bytes through pure decoders and the owned store, plus real-entrypoint synthetic fixtures with UI/brokers disabled for migration/lifecycle evidence. #34 supplies future verified request/profile/permission context through the shared coordinator; #35/#36 own bounded public presentation; #37 owns separately authorized real-device/soak validation. Deployed firmware/capability/permissions remain unknown, and a timeout is not proof of unsupported hardware.

Keep JavaScript ES modules, current approved dependencies, structured safe logs, schema/version ownership and container startup behavior. All examples/defaults are declarative; no operator config/deployment is modified. Do not loosen CI coverage/read/write limits to fit the new feature. Status/sensor/neighbour units and partial semantics must be documented before later reporting consumes them.

### 6. Risks and Edge Cases

- **Padding/layout ambiguity:** 48-byte legacy and 56-byte current status plus the echoed four-byte tag both fit a 64-byte encrypted block, so the post-tag host body can be 60 bytes in both cases. Path-return metadata can yield other padding lengths. This is an inference from the verified framing sources, not a deployed-device observation; source profile/quality must be explicit.
- **Encoder comments versus implementation:** the pinned Cayenne header comments call voltage/current unsigned, but its actual `getTypeSigned` selects both as signed. Use tested encoder behavior for that profile and disclose incompatible variants; don't guess signedness from a generic LPP constants table.
- **Partial isn't empty:** unknown sensor types/padding/profile or missing environment fields cannot mean a healthy zero value, no configured sensors, a fully known battery state or a completely decoded response. A full decoded reply still isn't a complete physical sensor inventory.
- **Neighbours aren't inventory:** aging uses remote RTC arithmetic and can wrap; prefix collisions and changing pages stay visible. Full-key remote reports do not become verified local adverts/routes. Page/permission/profile variants can increase latest-retention cardinality; document retained volume rather than falsely promising a global storage cap.
- **Save-first disk growth:** unlimited default history and protected latest/fully-decoded snapshots intentionally favor offline use. Monitor the same owned volume; cleanup is synchronous and may cost more than an ordinary read/write. Pruning never promises a smaller SQLite file or complete lifetime coverage.
- **Unavailable authentication:** #33 cannot produce live telemetry until #34's separately reviewed authentication/routing/firmware policy is implemented. Generic request support alone doesn't certify rights, guest environmental access or management-safe login.
- **No universal build support:** sources are pinned, but deployed firmware/board/compile flags remain unknown. A stored interpretation profile is evidence metadata, not inferred independent firmware attestation. No broad runtime/framework/security boundary is changed just to fit this feature.
