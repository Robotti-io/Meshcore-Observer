## Request summary

P1-14 is the viewer/query layer for the historical datasets delivered by the
earlier Pillar 1 issues. The implementation should make those datasets
available through bounded, documented HTTP reads that the later dashboard work
in #36 can consume. It should not add new radio work, change MQTT publication,
or make the dashboard responsible for reconstructing historical state.

The API must distinguish acceptance-time measures from completion-time
outcomes, current inventory from retained event history, and observed evidence
from conclusions that the data cannot prove. A valid empty result is a normal
response and must carry enough range and coverage metadata for a caller to
explain that state.

## Codebase findings

### Existing HTTP seam

`src/web/metrics-server.js` is a synchronous `node:http` viewer over the
always-on `MetricsStore`. Existing routes already establish the compatibility
rules that new routes should follow:

- GET-only dispatch with generic 404/405 responses.
- Shared `parseRangeQuery()` and AJV schemas with `additionalProperties: false`.
- Half-open `[start, end)` windows resolved by `resolveRangeWindow()`.
- Bounded chart requests through `maxBuckets` and bounded list requests through
  `limit`/`offset`.
- Generic 500 responses with a structured application warning, without
  exposing database or stored payload details.

Existing dashboard responses and routes must remain byte-compatible for their
current consumers. New reporting routes can share the same helpers and logger,
but should not broaden the current unauthenticated binding or introduce a
second HTTP framework.

### Existing persistence seam

The store already has narrow query methods for the requested datasets; the
main gap is their HTTP contract, not a generic SQL endpoint. Relevant methods
include:

- `queryBotUsageTotals()`, `queryBotUsageGroups()`,
  `queryBotSenderCounts()`, and `queryBotOutcomeGroups()`.
  Accepted usage is scoped by `enqueued_at`; resolved outcomes are scoped by
  `resolved_at`. The `bot_replies` table also retains optional
  `senderIdentifier`, `senderIdentifierKind`, and `senderIdentifierSource`.
- `queryAdvertTotals()`, `queryAdvertTypeTotals()`, and
  `queryAdvertNodeCounts()`, backed by retained distinct advert events and
  separate current node inventory queries.
- `queryProcessHistory()`, `queryProcessSamples()`, and
  `queryRuntimeEvents()`, including run IDs, sampling gaps, and unavailable
  measurements.
- `queryTelemetryObservations()`, `queryTelemetryOutcomes()`, and
  `getTelemetryLatest()`, which already return bounded pages, retained-range
  coverage, freshness, clock-anomaly, and decoder metadata.
- `queryTopologyPaths()`, `getTopologyPath()`,
  `queryTopologyObservations()`, `queryTopologyRouteCounts()`,
  `queryTopologyCoverage()`, and `queryObservedProximity()`, which already
  carry lower-bound, pruning, and identity-resolution policy metadata.

The existing `queryRegionAnswers()`/outcome/publication reads are deliberately
excluded. OBS-02 remains an MQTT-only initial contract; adding a region HTTP
surface would be a separate scope decision.

### Existing validation and retention seam

The web schemas currently cover range-only, bucketed, dashboard, node-total,
and current-node-list requests. Metrics-specific schemas already validate the
store query shapes. The implementation should add web-facing schemas that
compose the shared range one-of with the relevant bounded filters instead of
passing arbitrary query objects into the store.

Historical rows are subject to the runtime-configured metrics retention and
explicit pruning policies. Responses therefore need to say `retained-range`
or another precise count scope where a result is not a complete historical
record. `range=all` must use the earliest retained timestamp relevant to the
dataset being queried; a dataset with no retained rows returns an empty result
with a null/empty coverage marker rather than inventing history.

## Proposed implementation plan

### 1. Freeze the viewer contract and shared query helpers

1. Document a common response envelope for new routes:
   `start`, `end`, the dataset payload, `countScope`, and a dataset-specific
   `coverage`/`policy` object where applicable. Empty pages use `total: 0` and
   an empty array; unavailable latest/current values use `null` plus an
   explicit freshness or availability field.
2. Extend the central web schema module with strict schemas for page filters,
   bucket limits, run IDs, bot filters, advert type filters, telemetry
   selectors, topology selectors, and proximity windows. Keep all unknown
   parameters rejected by AJV before store calls.
3. Extend range resolution so new datasets can provide their own earliest
   retained timestamp for `range=all`, while preserving the existing behavior
   of all current routes.
4. Define fixed maximum page and bucket costs at the web boundary. Store
   methods remain the final bounded read; no route may hydrate unbounded JSON or
   return raw handler-state/private message content.

### 2. Add focused historical reporting routes

Use separate, predictable route families so #36 can request only the data for
the active screen. The recommended first contract is:

- `/api/metrics/bots/usage` for accepted totals plus paged aggregate groups
  (bot, channel, trigger, sender name, and an approved stable sender
  identifier when available).
- `/api/metrics/bots/outcomes` for completion-time sent/failed/expired/
  cancelled groups, with bot/command/sender dimensions and outcome totals.
- `/api/metrics/adverts` for event/type totals and paged per-node event groups;
  `/api/metrics/nodes` remains the current inventory/totals route.
- `/api/metrics/process/history`, `/api/metrics/process/samples`, and
  `/api/metrics/runtime-events` for bucketed resources, bounded raw samples,
  and bounded lifecycle events.
- `/api/metrics/telemetry/observations`,
  `/api/metrics/telemetry/outcomes`, and
  `/api/metrics/telemetry/latest` for retained observations, poll outcomes,
  and a scoped latest read.
- `/api/metrics/topology/paths`, `/api/metrics/topology/path`,
  `/api/metrics/topology/observations`, `/api/metrics/topology/counts`,
  `/api/metrics/topology/coverage`, and `/api/metrics/topology/proximity` for
  passive path evidence and bounded proximity candidates.

Each route should be a thin adapter over an existing store method. It should
return stable field names, preserve policy metadata such as
`coverageIsLowerBound`, `detailMayBePruned`, and `freshness`, and avoid
reconstructing historical facts from the current node registry.

### 3. Preserve security, logging, and operational behavior

1. Keep the existing request/application logging sequence and stable
   `services.metricsUi` source. Schema failures may return only the request
   record plus security-appropriate diagnostics; valid requests continue to
   produce an application log.
2. Keep the existing loopback-first, unauthenticated viewer boundary. Do not
   expose credentials, bearer material, raw handler state, private message
   content, or telemetry secrets. Sender names are aggregate dimensions; any
   stable sender identifier requires an explicit privacy decision below.
3. Ensure all reads remain available while the dashboard HTTP server is
   disabled because persistence is owned by `MetricsStore`/`MetricsSampler`.

### 4. Verify contracts before dashboard integration

Add focused tests for schema rejection, range boundaries, dataset-specific
`range=all`, accepted-vs-completed timestamp semantics, empty/unavailable
responses, sender/privacy redaction, policy metadata, and page/bucket bounds.
Add route compatibility tests proving existing endpoints retain their current
responses and logging/error behavior. Add large-fixture bounded-read tests for
the new adapters where the corresponding store cost tests already exist.
Run `npm run lint`, `npm test`, and `npm run test:ci` before handing the API
contract to #36.

## Assumptions

- #35 is API/query work only; dashboard client changes remain in #36.
- Existing store schemas, retention settings, and pruning rules are the source
  of truth; this issue does not add a second history table for data already
  retained.
- Bot usage counts only records accepted after duplicate filtering. Repeated
  copies do not create additional usage rows. Acceptance is measured at
  enqueue/accept time and delivery outcomes at completion time.
- Bot interaction rows remain retained for the same configurable duration as
  other key metrics. Browsable individual interaction history remains deferred,
  but the backend aggregate and durable-record contract is preserved.
- Advert, topology, telemetry, and process responses are evidence reports. They
  must carry lower-bound/pruned/clock-anomaly information rather than imply
  reachability or complete history.
- OBS-02 region answers and publication history remain out of the HTTP API in
  this issue.

## Open questions

1. **Endpoint contract approval — resolved:** Adopt the focused route family
   above. Keep `/api/metrics/dashboard` and all existing routes backward
   compatible; #36 will consume the focused routes instead of adding new
   dashboard-only views.
2. **Sender identifier exposure — resolved:** Retain the validated stable
   identifier in SQLite and expose only a stable redacted form in the
   unauthenticated viewer API. A validated advertised public key is the
   identity key; the username is the display label and historical context, not
   a second identity component. A rename therefore remains associated with the
   same key, while duplicate names with different keys remain distinct. If no
   validated key or equivalent identifier exists, use the exact sender name as
   a name-only fallback and mark the evidence kind/source accordingly.
3. **`range=all` semantics — resolved:** New routes resolve `range=all` from
   the earliest retained record in their own dataset. Existing dashboard route
   behavior remains unchanged for compatibility. This avoids silently
   excluding bot, advert, process, or telemetry history when packet sampling
   started later.

## Risks and edge cases

- A range can be valid while having no retained rows because pruning occurred;
  responses must distinguish empty from unavailable and must not fabricate
  zero-duration coverage.
- `resolved_at` can be null for pending bot replies. Pending rows are excluded
  from outcome ranges but remain protected from pruning and from accepted usage
  counts unless they have a valid acceptance timestamp.
- Sender names are not guaranteed unique. Grouping must use exact binary name
  semantics and may include a stable identifier only when the producer supplied
  validated evidence.
- Current inventory survives event pruning and must not be used to recreate
  expired advert events or historical re-hear counts.
- Telemetry JSON is validated and bounded at read time; malformed retained
  records must fail as a generic stored-data error without leaking JSON.
- Topology paths are passive reception evidence. They are not verified outbound
  routes, and prefix associations can be ambiguous or pruned.
- Large `range=all` queries can be expensive even with a page limit if a count
  scan is repeated for every dimension. Keep total-count and page reads on
  indexed predicates, and reuse existing materialized/bounded store queries.
- The dashboard is intentionally unauthenticated. Any identifier or path field
  added to a response increases the impact of an operator binding the service
  beyond loopback and therefore needs the protected-boundary approval called
  out above.
