### 1. Feature Summary

- Connect the completed #35 bounded reporting APIs to the existing vanilla
  dashboard without rebuilding historical facts in the browser.
- Preserve the shared reporting-range semantics, clearly distinguish live
  state from retained history, and make partial/empty/stale/unavailable data
  understandable to operators.
- Extend the current dashboard's overview and detail seams for bot usage and
  outcomes, advert/node activity, topology evidence, repeater telemetry, and
  Observer runtime history while leaving OBS-02 region answers MQTT-only.

### 2. Relevant Existing Architecture

- `src/web/dashboard-page.js` owns the HTML shell, current navigation, range
  controls, live tiles, and existing overview/packet/broker/bot/repeater
  sections.
- `src/web/client/dashboard.js` owns fetch coordination, SSE live snapshots,
  selected-range state, rendering, stale/loading/error status, and table/chart
  updates. It already has latest-request-wins and SSE coalescing behavior.
- `src/web/client/dashboard-logic.js` contains DOM-free range, formatting,
  response-shaping, and chart helpers that can be extended without a browser
  shim or new dependency.
- `src/web/client/dashboard.css` provides the existing cards, status badges,
  responsive table wrappers, dark/light variables, and narrow-screen layout.
- `src/web/metrics-server.js` exposes the backward-compatible aggregate
  dashboard route and the focused #35 reporting routes. The browser should
  consume those bounded routes rather than adding a second data-access path.
- `test/web/metrics-server.test.js` covers server response contracts;
  `test/web/client/dashboard-logic.test.js` covers pure client behavior. The
  repository has no browser automation dependency, so visual/keyboard checks
  remain manual and documented.
- Pillar 4 #41/#43 own shared controls and navigation hierarchy. #36 consumes
  those seams and must not silently create a competing design system.

### 3. Proposed Approach

1. Freeze a view-to-endpoint matrix before coding. Keep the existing
   `/api/metrics/dashboard` route for compatibility and use the focused #35
   routes for newly exposed history/detail data. The selected range remains
   one in-memory state shared by every range-aware view; current connectivity,
   queue depth, and current inventory remain explicitly **Live**.
2. Keep the browser adapters thin. Add pure response mappers and state helpers
   to `dashboard-logic.js`; keep fetch/error/coalescing behavior in
   `dashboard.js`; keep SQL and bounded response assembly in the server/store
   layers already delivered by #35.
3. Extend the existing overview/detail layout in small slices. Add practical
   textual/table values beside charts, preserve exact values when Chart.js is
   unavailable, and avoid creating a top-level navigation item for every
   metric until the #41/#43 hierarchy is available.
4. Treat each dataset independently during refresh. A failed telemetry or
   runtime read must preserve healthy bot/node/packet sections and show the
   last successful timestamp plus the relevant retained-range/freshness
   limitation.
5. Keep all untrusted names, commands, identifiers, and stored labels inserted
   with text APIs or validated DOM attributes. Do not add a framework, chart
   library, CSP exception, authentication change, or OBS-02 HTTP surface.

#### T3: Connect bot, node/topology, telemetry, and runtime reporting

- **Objective:** Deliver the approved reporting data to usable overview and

- **Definition of done:** Existing views remain reachable, no section forces

### 6. Risks and Edge Cases

- The dashboard currently has a compact five-view shell. Adding telemetry and
  runtime surfaces without the #41/#43 hierarchy could create a crowded or
  unstable navigation model; T1 must settle placement first.
- Focused endpoints return retained history and policy metadata, not complete
  lifetime truth. The UI must never label pruned/lower-bound data as complete.
- Current inventory, live connectivity, and queue depth can change between a
  live SSE snapshot and a selected-range response. Keep their scope labels
  and timestamps separate.
- Partial API failures, malformed retained JSON, and a disconnected SSE stream
  must leave other sections usable and preserve the last successful values.
- Large bot/node lists and telemetry samples can overwhelm a browser even
  when server pages are bounded. Prefer summaries and explicit pagination or
  drill-down links over client-side hydration of every row.
- Chart.js is an optional CDN asset. Tables, summaries, and accessible text
  remain the authoritative fallback when the browser has no internet access.
- The dashboard is unauthenticated and loopback-first. Sender identifiers,
  public keys, path details, and stored labels must stay within the #35 privacy
  contract and use escaped text rendering.
