### 3. Proposed Approach

#### Strict normalized answer contract

Add pure `src/regions/region-response-parser.js` and centralized `region-schemas.js`. Validate `{body:[byte,...]}` with AJV before offsets/decoding; accept 4–170 bytes, read uint32 LE clock from the first four bytes and remove only trailing NULs from the remaining CSV bytes. Use Node's fatal UTF-8 decoder with BOM preservation, so invalid input cannot silently create replacement characters or lose a leading character. Reject embedded NUL, control characters, empty CSV items (including leading/trailing/doubled comma), and over-bound normalized data. An entirely empty CSV becomes `regions:[]`.

Preserve spelling, case, Unicode, literal whitespace, duplicates and returned order; do not trim, case-fold, sort, deduplicate, add/remove a `#`, or derive keys. Exact `*` is a wildcard entry, not an ordinary named-region identity. Bound the CSV to at most 166 UTF-8 bytes, region count to at most 83 (the one-byte-name/comma worst case), each nonempty name to that byte budget, and revalidate serialized aggregate length at the normalized store boundary. These are host safety bounds derived from #29's envelope cap, not a universal firmware region limit or a truncation detector.

Return normalized regions, `repeaterClock` (uint32, including zero), `bodyBytes`, `csvBytes`, `parserVersion:1`, `completeness:'unknown'` and fixed Companion attribution. The wire parser always has a clock; the durable normalized schema permits explicit null for a future unavailable clock and never fabricates zero. All fields use strict schemas; local semantic invariants follow schema validation. No raw bytes, tags, encrypted padding or arbitrary exception text is stored or logged. #32 must separately approve how the public `truncated` boolean maps from the pinned producer/firmware evidence; a short/empty answer and `truncated:false` cannot establish completeness.

#### Durable data model and atomic outcome recording

Add `src/metrics/region-migration.js` as **migration 14**, subject to confirming no intervening migration at execution, and `region-history.js` on the store's owned connection. No legacy answers or query evidence are fabricated. Use four tables:

| Table | Proposed data / constraints |
| --- | --- |
| `region_query_outcomes` | UUID request ID primary key; source run FK; uppercase full Observer/target keys; request-start and terminal observation times; typed `answered`, `failed` or `unsupported` outcome/reason; nullable actual route; explicit clock-anomaly flag. This is a terminal query evaluation ledger, not a physical-send counter. |
| `region_answers` | Non-recycled integer answer ID; unique request FK to an answered outcome; original Observer receipt time; JSON normalized regions; nullable repeater clock; body/CSV lengths, parser version, unknown completeness and Companion attribution. Store every successful observation, including unchanged/empty lists. |
| `region_latest` | Primary key `(observer_public_key,target_public_key)` referencing one immutable successful answer. This snapshot survives historical-detail pruning and radio replacement never merges reporters. |
| `region_publications` | Primary key `(answer_id,broker_id)`; `pending`, `publishing` or `published`; attempt count, last attempt/result times, next-due time and bounded error code; nullable source-run claim and UUID claim token. No broker URL, credentials, MQTT body or downstream-ingestion claim. |

Provide `MetricsStore.recordRegionResult({outcome, answer?, brokerIds:[]})` backed by strict discriminated schemas. Require the active owned run; success requires direct-route evidence and normalized answer, failure/unsupported forbids an answer. Trusted #31 supplies context from its captured request, not from payload identity. Validate before writes and atomically commit the terminal outcome, successful answer, possible latest update and requested broker rows. Use fixed prepared SQL, FK/CHECK constraints and no external SQL. Exact repeat of one request ID is idempotent; different content/context for that ID is a conflict and rolls back. Repeating an already-recorded result must not reset publication acknowledgements or add newly supplied destinations; use the separate explicit staging method for broker changes.

Failures preserve the previous successful declaration and never create `[]` or publication work. Do not persist `deferred` polls (`busy`, foreground, rate/quiet/queue waits) as individual attempts. Terminal unsupported/failed evaluations can be recorded by #31's bounded policy; no generic per-poll database/log write is introduced. Capture loss or death before recording a terminal result remains missing evidence: no durable in-flight RF transaction is fabricated or replayed at startup. #31 retains transient correlation, applies backoff and integrates safe fixed warnings if persistence fails.

Latest selection uses greatest `observedAt`, with stable answer ID as a deterministic tie-break; late-arriving older observations enter history without replacing newer answers. Clock anomaly remains explicit. If different declarations share one reporter/target/millisecond timestamp, preserve both locally, flag that timestamp group as ambiguous and make it ineligible for automatic publication until a later unambiguous observation. Never invent a newer timestamp to evade CoreScope's idempotency key. Identical declarations at the same timestamp may remain separate local observations; their publication staging deduplicates the equivalent public identity. A collided outstanding claim cannot certify or retry a now-ambiguous group; its conditional resolution must fail safely, with no false ingestion claim. Already-transmitted content cannot be undone.

#### Freshness and bounded internal reads

Propose `PACKETCAPTURE_REGION_ANSWER_FRESHNESS_HOURS=72`, whole hours **1–8760**, with central code defaults, strict raw/normalized validation and matching `.env.example`. This is answer-age labeling only: it neither authorizes RF nor schedules refresh, changes the approved 72-hour direct-advert window, nor deletes stale declarations. Future #31 cadence is separate and must be chosen against this policy.

Expose `getRegionLatest({observerPublicKey,targetPublicKey,now,windowMs})`, `queryRegionAnswers`, `queryRegionOutcomes` and `queryRegionPublications`. Require explicit reporter scope for current answers; history filters support reporter/target/run and half-open `[start,end)` times. Answer history ranges use receipt time; outcome ranges use terminal time. Default page size 100, strict maximum 200, deterministic time/ID ordering and bound SQL parameters; no general query or public endpoint. Return answer presence (`unknown`, `empty`, `non-empty`) separately from freshness, latest terminal outcome, unknown completeness, time ambiguity and retained-history availability. A failure and an older stale answer can coexist.

Age uses Observer receipt time, never repeater clock/publication time. Age equality is stale; future-dated answers and timestamp-conflict groups are not fresh. Guard wall-clock rollback with a process query high water plus persisted run last-known-alive evidence, following topology's existing approach; return clock flags and effective time without mutating original observations. A rollback cannot make an expired answer fresh; an unusually future clock may conservatively delay freshness until clocks agree. Latest-time ordering does not establish actual chronological freshness when clock anomalies exist.

Add indexes for reporter/target/receipt time, terminal time/run, latest pair lookup and per-broker publication status/due/answer ID. Query bounds constrain result/working memory, not total retained disk. Test realistic retained history and query plans; do not add an ORM or separate cache/store.

#### Publication state, crash recovery and delivery limits

`brokerIds:[]` stages no work by default. Up to 64 distinct explicitly supplied broker IDs (1–256 characters) bound one transaction's fan-out; these are region-feature storage bounds, not changes to existing general broker configuration. #32 must validate its opted-in IDs against these limits and use stable IDs; reusing one ID for a different destination is an operator configuration concern and must not silently inherit a previous acknowledgement.

Provide explicit `stageRegionPublications({answerId,brokerIds})`, `claimRegionPublication({brokerId,runId,now})` and token-conditional `resolveRegionPublication({answerId,brokerId,claimToken,...})`. Stage only validated, unambiguous immutable answers; duplicate staging preserves prior progress. Query/claim at most one due item per call, returning a snapshot with its original reporter/time/regions. A strict bounded allowlist records failed/skipped transport outcomes; raw broker errors and secrets never enter this dataset. Retry makes the same item pending with caller-supplied next-due time; #32 owns delay/cap/opt-in checks and actual MQTT interaction, not this store.

Claims require current exclusive run ownership. On a new owned run, recover previous `publishing` rows to pending inside `beginObserverRun()`'s transaction, clear stale tokens, preserve answer/time and retain unknown acknowledgement status rather than claiming delivery. Old tokens cannot resolve new claims; no timer/worker starts in #30. `published` means the future publisher's approved transport-success criterion, never proof of CoreScope ingestion. Crash after broker acceptance but before local acknowledgement can cause duplicate retries; the immutable downstream identity supports idempotency, not exactly-once delivery.

Retain each staged observation independently, rather than silently replacing older undelivered answers with the newest. Disabled/removed brokers do not trigger sends or purges; pending rows remain saved until their separately approved owner handles them. Backfill to newly enabled brokers, broker configuration fingerprints, retry cadence/QoS and terminal abandonment are #32 choices. This contract supplies recoverable storage without selecting destinations or enabling publication here.

#### Save-first retention and operator implications

Use shared `PACKETCAPTURE_METRICS_UI_RETENTION_DAYS` for answer/outcome/publication history, unlimited when zero. Keep one latest successful snapshot per reporter/target indefinitely, even stale or empty. Protect all pending/publishing answer references. No new latest-answer purge switch is proposed in #30; explicit future purge would require its own reviewed scope.

Extend existing transactional `pruneOlderThan(cutoffMs)`: remove old published bookkeeping only when its result is before cutoff; remove historical answer rows only when both receipt/outcome times precede cutoff, no latest pointer references them and no publication reference remains; remove terminal outcomes only after their answer reference is gone. Equality remains retained under the existing `< cutoff` convention. Protected rows keep source-run references valid; prune run parents last. Latest and pending state remain queryable when other history is unavailable. No pending data is abandoned to honor a nominal retention duration; even published records can protect an answer until their own result-time cutoff.

Unlimited history/offline publication can grow disk indefinitely. Bounded rows per operation and packet-size bounds are not a lifetime disk cap. Document usage monitoring, FK-protected older runs, backup-before-upgrade/rollback, recovery uncertainty and SQLite page reuse without claiming automatic file shrinkage. No raw packet archive is added.

### 6. Risks and Edge Cases

- Protocol omission is undetectable even for a short/empty list; completeness stays unknown. Successfully decoded content is an observation from the trusted Companion, not cryptographic proof of a repeater's entire configuration.
- Millisecond timestamp conflicts and wall-clock rollback can disagree with actual receipt sequence and downstream deduplication. Preserve evidence, expose uncertainty and suppress ambiguous automatic publication without manufacturing time.
- Terminal outcomes describe evaluated work and are a retained lower bound, not all attempted RF sends or all operational deferrals. Crash before storage leaves unknown evidence; do not publish or infer an empty declaration from it.
- A database write can fail after a valid RF reply. Surface a safe storage failure without losing an earlier successful answer or triggering an immediate resend; #31 owns future bounded retry/backoff integration.
- Persistent outbox rows make delayed/restarted delivery possible but cannot guarantee downstream ingestion/exactly-once delivery. Failure after network send may require an idempotent duplicate; #32 must define the transport-success criterion.
- Pending publications, latest snapshots and their run FKs deliberately survive history retention. Long outages and disabled brokers can retain older rows indefinitely; capacity monitoring is required under save-first policy.
- Broker IDs are currently only nonempty in general configuration. The new bounded opt-in region schema must be acknowledged in #32; it does not retroactively reject or change existing capture brokers.
- Migration rollback is transactional; application downgrade after migration 14 is not automatically safe. Back up the closed owned database and document restoring that backup rather than ad hoc schema deletion.
