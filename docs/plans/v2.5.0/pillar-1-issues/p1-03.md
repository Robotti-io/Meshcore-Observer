### 1. Feature Summary

Persist Observer run identity, start/version metadata, last-known-alive evidence, clean stop when available, and retained cumulative runtime. Report abrupt endings honestly without guessing the exact stop time.

### 2. Relevant Architecture Before Implementation

- `src/index.js`: validates configuration before side effects, opens MetricsStore unconditionally, starts services, and registers SIGINT/SIGTERM shutdown with a 10-second bound. It currently closes the store before the final MQTT/radio teardown; clean-end recording must account for that ordering.
- `src/metrics/sampler.js`: always-on configurable periodic sampler, independent of HTTP enablement; uses shared retention and stops before store close. It is the existing cadence seam for last-known-alive checkpoints.
- `src/health/service-health.js`: has an in-memory `startedAt` for existing live UI uptime; no durable run identity. Keep existing live uptime semantics unless #35/#36 separately review a change.
- `src/metrics/store.js`: transactional migrations, synchronous prepared statements, WAL/foreign keys, and narrow query methods. No run table currently exists.
- `test/index.test.js`: already covers entrypoint shutdown using Node event emission to accommodate Windows signal behavior. Store/sampler tests provide time/reopen fixtures.

### 3. Proposed Approach

Propose one generated `randomUUID` run identity per successful Observer startup and one database-local persisted instance UUID, independent of radio name, IATA or hardware public key. Copying the database copies its identity/history; creating a new database begins a new history. Do not add a host-bound identity file, hostname inventory, secrets, or configuration fingerprints.

Capture bootstrap start wall time and a monotonic elapsed-time baseline at entry to `main`; persist the run after configuration validation and successful store opening, before hardware/network services start. Failed configuration or an unopened store cannot produce a durable run record. Store application version, Node version, platform and architecture as explicit non-secret metadata. PID is unnecessary for historical identity.

Propose `observer_runs` with run ID, instance ID, start time, last-known-alive time, persisted observed-duration ms, nullable ended time, nullable reason, and state `running`, `clean`, or `unclean`. Heartbeats store monotonic elapsed duration and a reception wall-time checkpoint at the existing sampler cadence. Last known alive is evidence, never a fabricated exact death time. At the next startup, mark prior unclosed runs `unclean` without filling in `ended_at` or extending duration through downtime.

For clean shutdown, stop accepting work, stop schedulers/sampler, close MQTT/radio while the store is still available, and write the clean end only after the bounded normal teardown succeeds. Then close the store. A forced timeout or failure before that write leaves the row unclosed for conservative recovery. Preserve the shutdown bound and existing pending reply recovery.

Define run duration using monotonic elapsed time, avoiding negative/inflated duration if wall time changes. Retained cumulative runtime is the sum of stored observed durations for retained runs, including the latest checkpoint for the active run; unclean runs contribute a known lower bound. Do not claim a lifetime total after history pruning or add downtime between runs.

Approved shared metrics retention applies to ended run history, preserving active runs and parents referenced by retained SQLite FK children. Run details can outlive the cutoff while required as a parent. Later process datasets must prune expired children before unreferenced parent runs transactionally. No extra heartbeat setting: reuse existing configurable sample cadence/default 10,000 ms. The user's delegated judgment and proceed approval resolve these choices.

### 6. Risks and Edge Cases

- Existing shutdown closes storage early; a late clean-write requires a deliberate small ordering change and timeout/failure tests.
- Single active process per database is the proposed supported operating model. Do not mark another live process unclean without deciding how concurrent use is handled; this plan does not silently add leases or multi-writer service coordination.
- Wall-clock timestamps support chronological display but are not the source of elapsed duration. Range attribution around clock jumps must not imply exact unobserved activity.
- Startup failures before the store opens cannot be persisted. Configuration errors remain visible through the current fail-fast path.
- Pruned run rows mean cumulative reporting covers retained evidence, not complete lifetime activity.
