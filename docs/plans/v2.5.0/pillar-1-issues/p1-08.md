### 1. Feature Summary

Provide one shared owner for an outstanding remote repeater request, from admission until response or terminal failure. Keep the existing command queue responsible for command acknowledgements and the existing airtime seam responsible for conservative transmission. Background discovery/telemetry must defer to bot replies and pending adverts and never build an unbounded queue or replay a backlog after reconnect.

Deliver the internal coordination foundation with deterministic tests and idle startup integration. #31/#34 later add actual opt-in producers, route/contact eligibility and polling cadence; #30/#33 own durable queryable results. Installing this foundation alone adds no periodic RF requests.

### 2. Relevant Existing Architecture

- `src/radio/radio-manager.js` owns serial/TCP connection, handshake, reconnect and shared `runCommand`. It captures a connection when a callback is queued but does not recheck that connection when the callback executes. Disconnect can leave an SDK command promise unsettled. Stop clears the connection before closing, so explicit coordinator shutdown is required.
- `src/radio/command-queue.js` serializes callback promises. Preserve this simple seam; do not hold its lease for a remote RF answer or introduce a generalized scheduler.
- `src/radio/airtime-coordinator.js` reserves one send after the configured quiet window. Acquire its reservation inside the actually executing command callback, immediately before transmission, and release after ACK/error. Do not reserve it while waiting in the command queue or awaiting an RF answer.
- `src/bots/reply-queue.js` exposes pending reply size; the always-on store exposes persisted pending/sending flood advert state. Existing reply/advert consumers keep their current behavior. A trusted foreground-work predicate can check these at remote admission and again at actual dispatch.
- `src/config/index.js`, config schemas, `.env.example`, shared AJV and structured logger are established seams. Runtime lifecycle is assembled in `src/index.js`.
- Installed MeshCore.js 1.15.0 exposes `sendCommandSendBinaryReq`, raw `rx` frames and a custom emitter. Its legacy one-shot remote helpers are unsuitable for this ownership contract. Anonymous API remains unavailable; [upstream PR #44](https://github.com/meshcore-dev/meshcore.js/pull/44) remains open. Firmware accepts only one aggregate pending remote operation.

### 3. Proposed Approach

#### Request contract and scope

Add focused radio modules for centralized remote schemas, bounded envelope parsing and coordination. Use the existing transport and shared AJV; no second MeshCore decoder or dependency. Validate descriptors before admission and all owned raw response frames before offsets/correlation/business logic. Schemas use `additionalProperties:false` and bounded byte arrays; parsing cannot retain raw frames in logs/storage.

The internal request descriptor carries a UUID request ID, exact normalized full target public key, operation kind and bounded operation-specific parameters. Allow only read requests: tagged binary status (01), telemetry (03), neighbours (06), and a future anonymous-regions (01 / reply path 00) capability. No arbitrary management/ACL/login command is accepted. T1 derives exact parameter/length schemas and byte fixtures from the pinned source; status, sensor mask and neighbour version/count/offset/order/prefix width are explicit. Body interpretation/storage stays #30/#33. Anonymous dispatch returns `unsupported` without side effects while the installed connection lacks the separately approved adapter; #29 does not implement that adapter or upgrade the library.

Route/contact/ACL eligibility comes from a trusted producer dispatch predicate, separate from the serialized DTO. It runs again inside the actual queued callback before sending. #31 must establish an existing exact-key zero-hop contact and fresh verified-zero-hop evidence; #34 must establish approved contacts/routes and guest-only authorization. The coordinator itself creates no contacts, changes no paths and accepts no credentials. Future login support must enter this same ownership/budget seam under #34's separately approved authentication contract; remote helpers cannot bypass it.

#### Ownership and state transitions

1. `tryRequest` validates and either returns a typed deferral (`busy`, `disconnected`, `not-ready`, `foreground`, `quiet-air`, `rate-limited`, `ineligible`, `unsupported`) or synchronously reserves the sole remote context. There is no remote backlog; producers retry through their own normal cadence, not a coordinator retry loop.
2. Capture immutable connection generation, Observer key, full target and operation. Require completed handshake/clock/device-query readiness, not merely `isConnected()`. Bound admission-to-command-start waiting by the configured ACK timeout. On queue expiry, cancel that remote callback logically so it performs no later send.
3. At command execution recheck generation, readiness, priority and trusted eligibility. Acquire shared quiet-air reservation at this point. Attach an owned `on('rx', handler)` before the low-level write, using exact `off` for cleanup; do not use high-level `once` remote helpers.
4. Hold the command/airtime transaction until validated Sent or Err, bounded by ACK timeout including a hung write. Sent fixes the request tag and records actual direct/flood result. Release command/airtime after ACK, but hold remote ownership awaiting the matching binary response. Signing, bot sends, adverts and capture can continue during that wait.
5. Bound response wait to `min(responseTimeoutMaxMs, max(1000, estimatedTimeoutMs + 1000))`. Use monotonic deadlines and strict uint32 estimates; absurd estimates never create an unbounded timer. A matching body is returned as bounded data with request context for the owning feature's strict parser. Ignore unrelated tags/types without consuming the handler. Pre-ACK responses are ignored, not guessed or buffered into an unbounded queue.
6. Resolve exactly once on response, command error, response timeout, route mismatch, protocol error, disconnect, shutdown or generation replacement. Detach listeners, cancel timers and clear the context on every terminal path; callbacks already scheduled by the SDK must check generation/settled state. Reject known recently retired tag reuse; use a fixed 32-entry set retained for `responseTimeoutMaxMs + 60000`, across reconnect within this process. This bounds memory and rejects observed reuse; it is not cryptographic replay protection across restart/arbitrary RF delay.

Use only tag correlation, never a key-prefix fallback, for successful binary completion. BinaryResponse lacks a full sender key; outcomes explicitly mean a tag-matched response attributed by the trusted Companion to the submitted context. Acceptance's old-session isolation is enforced by generation guards/listener cleanup, without claiming impossible global RF replay guarantees.

#### Ambiguous ACK recovery and operational errors

When a written command has no valid ACK, its write fails ambiguously, or its ACK is malformed, invalidate **only the captured transport generation** before allowing another queued command. Close that connection and use RadioManager's existing reconnect policy; no device reboot or firmware change. Previously queued callbacks for that generation fail without executing on either the old or replacement connection. Race in-flight queue work with generation termination so an abandoned SDK promise cannot block all later work; account for late resolution without unhandled rejections.

Bound connection-close settlement using the existing shutdown deadline seam where available. If closing the old transport cannot be established, fail closed for new remote dispatch and report the condition rather than declaring it safe to reuse. Do not reconnect two simultaneously usable transports. A normal *post-ACK response timeout* releases the remote context without unnecessarily reconnecting the radio.

Emit an actionable stable warning such as: “Remote request acknowledgement timed out; the radio connection is being reset to prevent a late acknowledgement from being assigned to another command.” Include allowlisted operation/outcome/request ID/phase metadata, never payloads, passwords, raw SDK errors or configuration dumps. Use standalone `services.remoteRequests` application logs without `reqInfo.requestID`; preserving the logging contract requires no HTTP change. Deferrals must not create a 250ms warning storm.

#### Priority, limits and configuration

Give pending bot replies or persisted pending/sending adverts priority at admission and dispatch. Background work can starve on continuously busy air; that is a disclosed opportunistic collection limitation, not grounds to force a burst. No backfill, automatic retry, new poll timer or foreground scheduling rewrite is added.

| Proposed setting | Default | Strict whole-number bounds / meaning |
| --- | --- | --- |
| `PACKETCAPTURE_REMOTE_REQUEST_ACK_TIMEOUT_MS` | 5000 | 1000–30000 ms; separately bounds queued admission and write/ACK phase. |
| `PACKETCAPTURE_REMOTE_REQUEST_RESPONSE_TIMEOUT_MAX_MS` | 30000 | 1000–120000 ms; caps Companion estimated RF wait plus 1000ms margin. |
| `PACKETCAPTURE_REMOTE_REQUEST_MIN_INTERVAL_MS` | 60000 | 10000–3600000 ms; monotonic spacing between physical remote send attempts. |
| `PACKETCAPTURE_REMOTE_REQUEST_MAX_PER_MINUTE` | 1 | 1–6; aggregate attempts in a sliding monotonic minute across producers. |

All physical attempts, including write failures and unexpected flood, consume budget; pure admission deferrals do not. Initialize the first eligible send no earlier than one configured interval after coordinator start; reconnect does not erase the budget or trigger catch-up. Defaults and units must match central code and `.env.example`; omitted values use defaults, explicit blank/fraction/out-of-range values fail startup before store/hardware/network effects. These approved limits are implemented in T4, including omitted-value defaults and matching example configuration. #31/#34 may impose stricter per-target cadence/backoff and cannot bypass these shared ceilings.

The retired tags, budget and pending ownership are transient bookkeeping. #29 adds no SQLite table, migration, public HTTP/SSE/MQTT field, auth behavior, dependency or deployment change. Its eventual queryable outcomes belong in #30/#33.

### 6. Risks and Edge Cases

- ACKs are untagged at the command-transaction layer; missing ACK recovery can briefly interrupt capture while reconnecting. It is safer than assigning a late acknowledgement to unrelated work, and needs the explicit operator explanation above.
- Pinned firmware emits Sent before processing a later remote response. A different deployment may violate that assumption; pre-ACK responses are not accepted as success and real-device activation remains separately validated.
- Shared deadlines must handle SDK callbacks queued with `setTimeout(0)` and promises that never settle. Merely racing a timer without exact listener detachment/generation guards is insufficient.
- A direct/flood result arrives after RF send; a route mismatch cannot undo the transmission. Zero-hop route assurance belongs in #31 dispatch preflight, with external route changes still a disclosed limitation.
- Tags are time-derived and host BinaryResponse contains no full sender key. Known reuse is rejected; unknown replay across process restart is not provably distinguishable. Do not advertise cryptographic full-identity correlation.
- Continuous foreground traffic can defer remote work indefinitely. Freshness/coverage reporting must explain that in future owning features. Raising limits is an explicit operator override, not an automatic response to incomplete data.
- #29 generic tagged binary support is available in the installed library; anonymous availability remains #31's upstream/artifact gate and should not block this independent seam.

Length limits reject trailing-newline keys/IDs as well as malformed patterns. Status and anonymous-regions require empty params. Response input is `{bytes:[...]}`, matching installed serial/TCP application-frame arrays. Binary response body is 1–170 bytes after the six-byte header. Zero body is malformed; a deliberate empty region answer still has its clock/padding. Sent is exactly ten bytes, route result 0/1 and unsigned uint32 LE tag/estimate; Err is exactly two bytes, known codes 1–6 get typed reasons and unknown byte codes remain unknown.
