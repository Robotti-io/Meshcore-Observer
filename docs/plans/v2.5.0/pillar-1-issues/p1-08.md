# [v2.5.0][P1-08] Coordinate remote requests and conservative radio scheduling

**GitHub issue:** [#29](https://github.com/Robotti-io/Meshcore-Observer/issues/29)

**Parent epic:** [Pillar 1 — #18](https://github.com/Robotti-io/Meshcore-Observer/issues/18)
**Type:** Feature
**Stage:** Issue scoped; implementation plan pending.

## Outcome and scope

- Establish the smallest shared remote-request ownership seam covering completion, timeout, error, and connection change.
- Coordinate discovery and telemetry with existing command serialization/airtime reservation; define bounded scheduling and priority so active polls do not starve bot replies or existing radio work.
- Discard old-connection correlation state and prevent unrelated responses from resolving the current request.

## Dependencies

- [P1-01 — #22](https://github.com/Robotti-io/Meshcore-Observer/issues/22)

Dependencies describe information/integration needed before implementation; independent planning can proceed using approved interfaces. Resolve external support and protected-boundary choices in the applicable plan.

## Acceptance criteria

- [ ] At most the protocol-supported number of remote requests is outstanding; ownership lasts beyond the initial command acknowledgement.
- [ ] Busy/disconnected conditions defer bounded work without bursts, leaks, or retry storms.
- [ ] Timeout/error/disconnect release ownership safely; old tags/responses cannot affect a new connection.
- [ ] Existing bots/adverts/capture remain compatible under mixed-workload timing tests.

## Validation expectations

Deterministic concurrent request, timeout, reconnect, quiet-air, priority/starvation, and lifecycle tests; npm test and npm run lint.

## Existing seams and approval decisions

src/radio/radio-manager.js; command-queue.js; airtime-coordinator.js; existing reply/advert consumers.

Approve concrete internal seam/scheduling choices before implementation; avoid a generalized scheduler rewrite.
