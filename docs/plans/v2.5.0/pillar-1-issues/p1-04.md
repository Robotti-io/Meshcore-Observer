### 1. Feature Summary

Persist CPU/memory measurements and a small typed operational-event history for each Observer run, using the existing sampler cadence and shared retention. Keep missing values distinct from zero and avoid duplicating the log stream.

### 2. Relevant Existing Architecture Before Implementation

- `src/metrics/sampler.js`: periodic always-on tick, sample persistence, once-daily shared retention, and optional dashboard sample emission. It currently stamps samples with wall time and has no CPU/memory collection.
- `src/web/metrics-sample.js`: computes packet/broker interval deltas from ServiceHealth; reuse this behavior without inserting process-CPU arithmetic into a web helper.
- `src/health/service-health.js`: snapshots current radio, broker and bot readiness. It already counts radio reconnects, packets and publish outcomes; no persisted typed event vocabulary exists.
- `src/index.js`: owns service construction and event wiring. Radio emits connected/disconnected/error; MQTT manager currently emits broker.connected but has no matching manager disconnect event. Do not assume unavailable event hooks exist.
- `src/config/index.js`, `schema.js`: existing sample interval defaults to 10,000 ms and validates a minimum of 1,000 ms; shared retention defaults to 0/unlimited. Both are independent of dashboard serving.
- Pushed #24 supplies durable run IDs, monotonic checkpoints and parent-retention semantics. Existing store/sampler/health/entrypoint tests are the primary regression seams.

### 3. Proposed Approach

Add a small process-measurement module using Node built-ins and injected measurement/clocks for tests. Capture `process.cpuUsage()` deltas over actual monotonic elapsed time and `process.memoryUsage()` values in bytes for RSS, heap total, heap used and external memory. Propose CPU percentage relative to one logical CPU: `100 * (userDeltaUs + systemDeltaUs) / elapsedUs`; it can exceed 100 for multi-thread activity and must not be clamped or mislabeled as total-host capacity. First/reset/invalid measurement intervals produce null CPU percentage, not zero; samples include actual elapsed interval.

Persist `process_samples` keyed by sample ID, associated run ID and Observer sample time, with explicit raw CPU delta/elapsed units and nullable derived CPU percent. Keep existing packet samples and their consumers unchanged. Use the same MetricsSampler tick and config cadence, not a new high-frequency timer. Store a valid process sample and corresponding run heartbeat atomically where practical after #24's seam is approved; isolate optional collection failures so packet capture continues.

Propose typed `runtime_events`: run ID, observed timestamp, enum kind, optional logical service ID, and strictly allowlisted state fields. Initial kinds are radio connected/disconnected/connect-error and broker/bot readiness state transitions. Use available radio events; derive broker disconnected/readiness changes from consecutive sampled snapshots when an event hook is absent, labeling timestamp as transition-observed time with sample-resolution uncertainty. Repeated identical states do not produce new events. Startup/run-end remain represented by #24; remote polling events are added by their owning future issues. Never store unrestricted error strings, message bodies, credentials, raw configuration or every application log line.

Use a configurable event-rate budget to bound transition/error volume: propose `PACKETCAPTURE_RUNTIME_EVENT_MAX_PER_MINUTE=60`, positive bounded integer with matching example/code fallback; exact bounds and suppressed-event accounting must be reviewed. Persist a non-sensitive suppression count with the next sample when the budget is exceeded so throttling is visible. This rate budget is separate from sampling cadence.

Propose shared metrics retention for process samples/events, pruned by Observer sample/event time with `[start, end)` range reads; retain run parents while referenced. Begin by evaluating built-in event-loop utilization using a deterministic delta seam. Include it only if review establishes clear units/baseline and measured acceptable overhead; defer delay-histogram collection until justified. No dependency or public API changes.

### 6. Risks and Edge Cases

- CPU >100% is valid under the proposed normalization. Host/container core quotas are not inferred from a guessed CPU count.
- Timer delay requires actual elapsed intervals. Sample timestamps alone cannot establish precise transition occurrence or resource use during unobserved gaps.
- `DatabaseSync` writes occupy the event loop; batch modest work and validate overhead with retained data rather than adding new database tooling.
- Event volume can surge during failures; the reviewed rate budget and suppressed counts are required before collector rollout.
- Run foreign keys and parent pruning depend on #24; migrations must be sequential and allocated only when implementation order is fixed.

### 10. Implementation and validation evidence — 2026-10-08

Migration 12 adds `process_samples` and `runtime_events`, both FK-linked to `observer_runs`, with stable AUTOINCREMENT row identities and observation/run/kind indexes. It invents no legacy samples/events and preserves migration 11's run/instance data. Strict centralized AJV covers native readings, derived DTOs, runtime event vocabulary, budget/configuration and bounded query inputs. Native failures affect only their measurement family; first/reset/invalid intervals remain null, while true zero remains zero. CPU measures one logical CPU using actual monotonic elapsed intervals; memory uses byte gauges. ELU uses active/idle millisecond deltas and a 0–1 fraction, independently from CPU and without a delay histogram or extra timer.

`RunHistory.checkpointEvidence()` provides the matching run/time/elapsed DTO. Sample and heartbeat writes commit together; an injected failed insert rolls both back. Foreign, ended or regressing runs cannot receive records. The same always-on sampler cadence persists process data with the dashboard off and no brokers/internet; optional collection/write failures retain packet/SSE behavior and fall back to ordinary checkpoints.

Typed radio hook observations and consecutive sampled broker/bot readiness transitions omit every raw error/configuration/message payload. Stable states produce no repeats; sampled transitions carry actual observation windows and do not claim exact occurrence time. A sliding monotonic 60-second attempt budget defaults to 60, whole override 1–600, matching central fallback/example.
