# [v2.5.0][P2-04] Launch secure local setup mode and configuration APIs

**GitHub issue:** [#69](https://github.com/Robotti-io/Meshcore-Observer/issues/69)
**Labels:** `release:v2.5.0`, `pillar:simplified-setup`, `enhancement`, `configuration`, `security`

**Parent epic:** [Pillar 2 — #19](https://github.com/Robotti-io/Meshcore-Observer/issues/19)
**Type:** Feature
**Stage:** Issue scoped; implementation planning pending.

## Outcome and scope

- Implement the approved explicit local setup entry point and administrative request boundary without requiring radio/MQTT/bot startup.
- Load safe current/candidate settings and validate bounded proposed actions through centralized schemas.
- Preserve approved HTTP logging/error/header/CSP contracts; any framework/security middleware dependency is separately approved.

## Dependencies

- [P2-01 — #66](https://github.com/Robotti-io/Meshcore-Observer/issues/66)
- [P2-03 — #68](https://github.com/Robotti-io/Meshcore-Observer/issues/68)

Dependencies identify required evidence/interfaces for implementation. They do not require finishing an entire consuming/owning epic before independent planning. Existing shared services retain their owning issue.

## Acceptance criteria

- [ ] New installations and invalid/offline runtime configuration can access setup locally.
- [ ] Host/origin/request authorization and sensitive API responses follow the approved security design.
- [ ] Stored secrets are not unnecessarily returned; malformed/unauthorized requests cause no state change.
- [ ] Normal observer/container startup behavior remains independent and compatible.

## Validation expectations

HTTP/bootstrap/schema/auth/request protection/secret response and lifecycle regressions; npm test and npm run lint.

## Existing seams and approval boundaries

Setup bootstrap/server, central config, existing node:http/static seams.

Follow AGENTS.md: JavaScript ES modules, centralized strict AJV/configuration/logging, existing seams, and always-on MetricsStore ownership. Concrete authentication, storage, public API/MQTT, dependency, logging-contract, CSP, and deployment changes require explicit approval in the implementation plan. Real hardware, service, privilege, restart, or network operations require the applicable authorization; issue capture performs none.
