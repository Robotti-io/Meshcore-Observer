# [v2.5.0][P2-01] Define setup architecture, local administration, secrets, and activation boundaries

**GitHub issue:** [#66](https://github.com/Robotti-io/Meshcore-Observer/issues/66)
**Labels:** `release:v2.5.0`, `pillar:simplified-setup`, `decision`, `configuration`, `security`

**Parent epic:** [Pillar 2 — #19](https://github.com/Robotti-io/Meshcore-Observer/issues/19)
**Type:** Decision
**Stage:** Issue scoped; implementation planning pending.

## Outcome and scope

- Specify independently launchable setup mode, normal startup behavior, local request authorization, secret visibility/permissions, and minimal privilege boundaries.
- Define multi-file candidate/active/known-good configuration, successful activation/offline behavior, restart versus live reload, draft persistence, and recovery ownership.
- Record runtime/container/manual configuration compatibility and explicit approval decisions without silently replacing existing config contracts.

## Dependencies

No child prerequisite. Begin with this scoped research/decision work.

Dependencies identify required evidence/interfaces for implementation. They do not require finishing an entire consuming/owning epic before independent planning. Existing shared services retain their owning issue.

## Acceptance criteria

- [ ] A reviewed decision record defines bootstrap, local administrative trust, request protection, and safe secret handling.
- [ ] Loopback binding alone is not treated as complete authorization; setup can work before valid runtime configuration.
- [ ] Atomic per-file replacement is not claimed as a multi-file transaction, and normal startup remains fail-fast/environment-driven.

## Validation expectations

Use first-run, malicious/local request, interrupted apply, offline save, failed activation, and existing-installation examples.

## Existing seams and approval boundaries

Config/bootstrap, node:http viewer seam, MetricsStore/configuration ownership.

Follow AGENTS.md: JavaScript ES modules, centralized strict AJV/configuration/logging, existing seams, and always-on MetricsStore ownership. Concrete authentication, storage, public API/MQTT, dependency, logging-contract, CSP, and deployment changes require explicit approval in the implementation plan. Real hardware, service, privilege, restart, or network operations require the applicable authorization; issue capture performs none.
