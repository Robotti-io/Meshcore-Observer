# Feature: Enhanced Bots

**GitHub epic:** [#20](https://github.com/Robotti-io/Meshcore-Observer/issues/20)

**Child issue register:** [Pillar 3 breakdown — 14 issues](pillar-3-child-issues.md), captured on 2026-10-07; implementation planning pending.

## Summary

Expand MeshCore Observer's bot capabilities so that bots behave more intelligently and efficiently on the mesh.

The primary goal of this pillar is not simply to add more commands. It is to improve how bots decide:

1. Which bot should respond to a request.
2. Whether a response is still necessary.
3. Whether a conversation should use public channel traffic or private/direct messaging.
4. How far a flooded bot response should be allowed to propagate.

MeshCore networks operate on constrained shared RF resources. As more bots and automated services are deployed, naïve bot behavior can result in multiple Observers responding to the same command, unnecessary flooded traffic, redundant replies, and messages propagating farther than intended.

v2.5.0 should introduce mechanisms that allow bot operators to deliberately control these behaviors.

The intended result is a bot system that remains compatible with simple channel commands while also supporting more targeted, cooperative, direct, and region-aware interaction patterns.

This work should build on the extensible command-handler and durable reply-queue architecture established in v2.4.0 rather than introducing another bot-framework rewrite.

---

## Goals

- Allow a user to explicitly address a particular Observer bot using the Companion name of the connected device.
- Allow individual bot commands to require explicit bot addressing.
- Preserve existing untagged/broadcast-style commands where desired.
- Support Companion names containing Unicode, emoji, and other valid user-facing characters.
- Allow selected bot commands to suppress their queued response when another participant has already satisfactorily answered the request.
- Record intentionally suppressed replies distinctly from failures or expirations.
- Support bot commands received through private MeshCore contact messages where protocol/library support permits.
- Prefer direct/private responses for private bot conversations where an appropriate route is available.
- Track ACK/delivery confirmation for direct messages where supported.
- Avoid describing ACKs as proof that a human user has read a message.
- Allow individual bot responses to specify an appropriate region/flood scope.
- Support the Companion Channel Scoping model being defined by the OKI Mesh community.
- Prevent scoped transmissions from leaking into an unintended broader flood because of shared radio state or concurrent bot activity.
- Minimize redundant RF traffic generated by Observer bots.
- Preserve existing reply scheduling, airtime coordination, persistence, configuration validation, and handler boundaries.
- Validate required capabilities against the installed/current `@liamcottle/meshcore.js` library and underlying MeshCore Companion protocol before implementation.

---

## Non-Goals

- Do not require every bot command to be explicitly tagged.
- Do not eliminate normal public-channel bot commands.
- Do not globally suppress replies merely because another arbitrary message was observed.
- Do not assume that any message mentioning the original sender represents a satisfactory response.
- Do not cancel replies that have already begun transmission.
- Do not assume that an observed inbound packet path is automatically a valid outbound route.
- Do not describe a direct-message ACK as proof that the human recipient read or viewed the message.
- Do not silently convert all bot conversations to private messaging.
- Do not automatically flood a response globally after a scoped or direct transmission fails unless the command explicitly permits that fallback.
- Do not hard-code OKI Mesh-specific region names into the core bot framework.
- Do not expose raw region transport keys as the normal operator-facing configuration model if a safer human-readable region model can be supported.
- Do not allow region-scope state changes to race between concurrent bot transmissions.
- Do not replace the v2.4.0 command-handler architecture simply to implement these capabilities.
- Do not assume protocol or library capabilities that have not been validated against supported firmware and `@liamcottle/meshcore.js` versions.

## Scope 1: Targeted Bot Commands / Bot Tag Matching

### 1.1 Problem

Multiple MeshCore Observer bots may listen to the same channel and support the same command.

For example, if several bots are configured to respond to:

```text
!echo
```

a single user request may cause every matching bot to prepare and transmit a response.

In many situations this is unnecessary.

Users should be able to explicitly address one bot so that only the intended Observer responds.

The identity used for this targeting should be derived from the Companion name of the device connected to the running Observer.

---

### 1.2 User Stories

#### 1.2.1 Explicit bot addressing

As a MeshCore user, I want to include the name of the intended Observer bot in a command so that only that bot responds.

For example:

```text
@[🤖Jeymz.011.OBV_BOT] !echo
```

Only the Observer whose connected Companion name is:

```text
🤖Jeymz.011.OBV_BOT
```

should execute the command.

#### 1.2.2 Configuration-level targeting

As an Observer operator, I want to declare that a particular command requires bot targeting without manually duplicating the Companion name in configuration.

A conceptual command definition may use a semantic token such as:

```text
{BOT_TAG} !echo
```

The exact configuration syntax should be finalized during implementation planning.

#### 1.2.3 Runtime identity

As an Observer operator, I want the bot tag to use the actual Companion name reported by the connected device so that renaming the Companion does not require manually changing every bot command.

#### 1.2.4 Mixed command behavior

As an Observer operator, I want some commands to require targeting while other commands remain globally callable.

For example:

```text
!stats
```

may remain a normal channel command while:

```text
{BOT_TAG} !echo
```

requires explicit bot targeting.

---

### 1.3 Functional Requirements

#### 1.3.1 Bot identity source

The bot's targetable identity should originate from the connected Companion device where supported.

The configuration should not require the operator to maintain a duplicate copy of the Companion name solely for command targeting.

If the Companion identity cannot be determined, commands requiring `{BOT_TAG}` must fail safely rather than matching every bot.

#### 1.3.2 Unicode support

Bot-name matching must support valid Unicode Companion names.

This includes:

- Emoji.
- Non-ASCII characters.
- Mixed Unicode and ASCII names.
- UTF-8-safe comparison.
- Names near supported MeshCore length boundaries.

The implementation should evaluate Unicode normalization requirements so visually equivalent names do not behave unpredictably.

#### 1.3.3 Tag syntax

The supported on-air targeting syntax must be explicitly defined.

A representative example is:

```text
@[🤖Jeymz.011.OBV_BOT] !echo
```

The parser should clearly distinguish:

- Opening tag syntax.
- Companion name.
- Closing tag syntax.
- Whitespace.
- Command trigger.
- Command arguments.

The exact syntax should be validated against actual MeshCore client behavior and community conventions.

#### 1.3.4 Matching behavior

A tagged command should execute only when:

- The command requires bot targeting.
- The supplied tag resolves to the current Companion's identity.
- The remainder of the command satisfies the configured handler's existing parsing rules.

A tagged command intended for another bot should be ignored.

#### 1.3.5 Existing command compatibility

Existing command definitions that do not require bot targeting should continue to operate normally.

Bot tagging should be an additive command capability rather than a breaking change to the command framework.

## Scope 2: Cooperative Response Limiting

### 2.1 Problem

When multiple bots support the same public command, several may independently queue replies to the same request.

Because the reply queue intentionally introduces timing and airtime coordination, another bot may successfully answer the request before this Observer's reply is transmitted.

For selected commands, continuing to send the queued response at that point provides little value and adds unnecessary RF traffic.

The bot should therefore be able to recognize that another satisfactory response has already been observed and suppress its own still-pending reply.

---

### 2.2 User Stories

#### 2.2.1 Command-specific response limiting

As an Observer operator, I want to mark selected commands as eligible for cooperative response limiting so that redundant replies can be suppressed.

#### 2.2.2 Observe another satisfactory reply

As an Observer bot, I want to inspect messages received while my own reply is queued so that I can determine whether the original request has already been satisfied.

#### 2.2.3 Preserve commands requiring multiple responses

As an Observer operator, I want commands without response limiting to continue responding independently because multiple responses may sometimes be useful or intentional.

#### 2.2.4 Report intentional suppression

As an operator, I want suppressed responses tracked separately from failures so that I can measure how much RF traffic the feature prevented.

---

### 2.3 Example Behavior

A conceptual exchange may look like:

```text
User:
!echo

Bot A:
Queues response.

Bot B:
Queues response.

Bot C:
Queues response.

Bot A transmits:
@[OriginalUser] <echo/path response>

Bot B:
Recognizes that the request has already been satisfactorily answered.
Cancels its still-pending reply.

Bot C:
Recognizes that the request has already been satisfactorily answered.
Cancels its still-pending reply.
```

The resulting lifecycle should conceptually distinguish:

```text
Bot A: sent
Bot B: suppressed
Bot C: suppressed
```

rather than treating Bot B and Bot C as failed or expired.

---

### 2.4 Functional Requirements

#### 2.4.1 Opt-in behavior

Response limiting must be explicitly enabled for a command.

A conceptual configuration option may resemble:

```json
{
  "trigger": "!echo",
  "limitDuplicateResponses": true
}
```

The final schema and option name should be determined during implementation planning.

Commands without this capability enabled must retain current behavior.

#### 2.4.2 Pending replies only

Only replies that have not begun transmission should be eligible for suppression.

Once transmission has started, the Observer should not attempt to cancel the RF operation.

#### 2.4.3 Correlation window

A possible competing response should only affect a pending reply when it occurs within the relevant lifecycle window for the original request.

At minimum, correlation should consider:

- Original request identity.
- Request sender.
- Original command.
- Time relationship.
- Pending reply state.

#### 2.4.4 Satisfactory-response detection

The Observer must not suppress a reply merely because another message mentions the original sender.

A competing response should meet command-appropriate criteria demonstrating that the request was likely satisfied.

Potential evidence may include:

- Addressing/tagging the original requester.
- Occurring after the original command.
- Matching expected response structure.
- Matching a handler-specific response type.
- Including expected command-specific content such as a path.
- Arriving before the local reply becomes committed for transmission.

#### 2.4.5 Handler-aware suppression

Different command types may require different definitions of a satisfactory response.

The architecture should allow command handlers or handler metadata to participate in suppression decisions rather than forcing every command through one universal text heuristic.

#### 2.4.6 Durable lifecycle state

If queued bot replies are persisted, intentional suppression should be represented as a distinct lifecycle outcome.

Potential outcome:

```text
suppressed
```

or another clearly defined equivalent.

It must remain distinguishable from:

- Sent.
- Failed.
- Expired.
- Cancelled for unrelated administrative reasons.

---

### 2.5 Reporting

Where bot metrics are available, response-limiting behavior should be reportable.

Example:

```text
Echo requests:          52
Replies sent:           31
Replies suppressed:     18
Replies failed:          1
Replies expired:         2
```

This provides evidence that cooperative suppression is actually reducing redundant traffic.

## Scope 3: Private Bot Conversations

### 3.1 Problem

Public channel commands and replies are convenient, but both consume shared flooded-channel airtime.

Some interactions are better suited to private MeshCore contact messages.

If a user has learned the Observer Companion through its advert, the user should be able to privately message that Companion with a supported bot command.

Where an appropriate direct route to the user exists, the Observer should respond privately instead of creating another public/flooded channel message.

Direct/private communication may also provide ACK behavior that allows the Observer to determine whether the destination MeshCore node acknowledged receipt.

---

### 3.2 User Stories

#### 3.2.1 Private command invocation

As a MeshCore user, I want to send a private message containing a supported command to the Observer bot so that my request does not need to be transmitted as public channel traffic.

#### 3.2.2 Private bot response

As a MeshCore user, I want a privately invoked bot command to receive a private response where supported.

#### 3.2.3 Direct routing

As an Observer operator, I want private bot replies to use an appropriate known route when possible so that unnecessary flooding is avoided.

#### 3.2.4 Delivery acknowledgement

As an Observer operator, I want ACK information for supported private responses so that I can distinguish messages that were transmitted and acknowledged from those that timed out or failed.

---

### 3.3 Example Interaction

Instead of:

```text
Public channel:

User:
!lookup E85C

Bot:
<public lookup response>
```

the user could interact through a private contact conversation:

```text
Private message to 🤖Jeymz.011.OBV_BOT:

!lookup E85C
```

and receive:

```text
Private response:

<lookup response>
```

with the Observer tracking the applicable delivery state.

---

### 3.4 Functional Requirements

#### 3.4.1 Private command intake

The bot framework should support recognized commands received through MeshCore contact/private messages where protocol/library support permits.

Private commands should reuse existing handlers wherever practical rather than creating entirely separate implementations of:

- `exact`
- `lookup`
- `stats`
- Future handlers

The transport should be treated separately from command semantics.

#### 3.4.2 Response transport selection

A handler should be able to produce a response independent of whether delivery occurs through:

- Public channel.
- Targeted public channel.
- Private/direct messaging.

Transport decisions should be made by the bot/reply-delivery layer rather than duplicated inside every handler where possible.

#### 3.4.3 Route selection

A previously observed inbound path should not automatically be treated as a guaranteed outbound route.

Potential route sources may include:

- Companion-maintained contact routing state.
- Returned-path information.
- Previously successful direct-message paths.
- Path/topology information collected by Pillar 1 where compatible and appropriate.

The exact route-selection model must be validated against the MeshCore protocol and `@liamcottle/meshcore.js`.

#### 3.4.4 Path freshness

A known route should not be assumed valid forever.

The implementation should evaluate:

- Route age.
- Previous send success.
- Previous ACK success.
- Companion-maintained path state.
- Path updates.
- Reset-path behavior.
- Appropriate retry behavior.

#### 3.4.5 ACK lifecycle

Where direct/private sends expose acknowledgements, the reply lifecycle should distinguish states such as:

```text
queued
sent
acknowledged
timed_out
failed
```

The exact state machine should align with actual protocol behavior.

#### 3.4.6 ACK semantics

An ACK should mean only what the MeshCore protocol guarantees.

The UI, metrics, and logs must not label an ACK as:

- Read.
- Viewed.
- Seen by user.

A safe interpretation is:

```text
Delivery acknowledged by destination MeshCore node.
```

#### 3.4.7 Fallback behavior

Failure of a private/direct response must not automatically result in an unscoped public flood unless that behavior is explicitly configured.

Potential policies may eventually include:

```text
direct-only
direct-with-retry
direct-with-explicit-flood-fallback
```

The initial implementation may support a smaller set after protocol behavior is understood.

---

### 3.5 Required Research

Review:

- MeshCore contact-message protocol behavior.
- Current `@liamcottle/meshcore.js` support for receiving contact messages.
- Current library support for sending private/contact messages.
- Expected ACK identifiers.
- ACK correlation behavior.
- Send-confirmed events.
- Timeout behavior.
- Retry behavior.
- Returned-path behavior.
- Companion-maintained contact paths.
- Whether raw observed paths from Pillar 1 can safely inform direct routing.
- How stale paths are represented or invalidated.
- Supported firmware/protocol versions.

If the required functionality is missing from the current dependency, any library upgrade or upstream contribution should be reviewed separately.

## Scope 4: Region-Scoped Bot Responses

### 4.1 Problem

The OKI Mesh community is introducing region-scoping guidance intended to reduce unnecessarily broad flooded traffic.

The community direction includes applying appropriate scopes to repeaters and having automated services such as bots use Companion Channel Scoping when transmitting responses on designated channels.

MeshCore Observer should support this behavior so bot responses can respect the routing scope appropriate to the command/channel rather than defaulting to an unrestricted flood.

---

### 4.2 User Stories

#### 4.2.1 Per-command region scope

As an Observer operator, I want to configure a region scope for an individual bot command so that its responses remain within the intended routing region.

#### 4.2.2 Different scopes for different commands

As an Observer operator, I want different commands to use different response scopes because not every bot function necessarily serves the same geographic audience.

#### 4.2.3 Default/channel behavior

As an Observer operator, I want commands that do not require an explicit override to use a defined default or channel-appropriate scope.

#### 4.2.4 Fail safely

As an Observer operator, I do not want a response configured for a limited region to silently become an unrestricted flood if region-scope application fails.

---

### 4.3 Conceptual Configuration

The final syntax must be aligned with the OKI Mesh Companion Channel Scoping specification and supported MeshCore APIs.

A conceptual configuration may resemble:

```json
{
  "trigger": "!stats",
  "responseScope": "region-name"
}
```

or:

```json
{
  "trigger": "!stats",
  "responseScope": {
    "mode": "region",
    "region": "region-name"
  }
}
```

These examples express intent only and should not be treated as finalized schema.

---

### 4.4 Scope Resolution

Operator-facing configuration should use meaningful scope identifiers wherever possible.

The bot configuration should not normally require an operator to manually derive or enter raw protocol transport keys when a documented region name or equivalent semantic identifier can be safely resolved.

The implementation must determine:

- How OKI Mesh region names are defined.
- How region names map to MeshCore transport/scope keys.
- Whether that mapping is static or derived.
- Whether channel configuration supplies a default region.
- How invalid/unknown regions are handled.

---

### 4.5 Transmission Serialization

Region/flood scope may be Companion radio state rather than a property passed atomically with an individual `sendChannelTextMessage()` operation.

If scope selection and channel transmission are separate radio operations, they must be serialized.

The following race must never be possible:

```text
Bot A:
Set scope = Region A

Bot B:
Set scope = Region B

Bot A:
Send reply
```

where Bot A's response accidentally uses Region B.

A scoped channel send should instead behave conceptually as one coordinated operation:

```text
Acquire radio command / transmit ownership
        |
        v
Apply required scope
        |
        v
Confirm scope operation if protocol permits
        |
        v
Transmit associated response
        |
        v
Restore/default scope if required
        |
        v
Release ownership
```

This should integrate with the existing command queue and airtime coordinator rather than creating an unrelated synchronization mechanism.

---

### 4.6 Scope State

The implementation must validate how the Companion treats flood-scope state.

Questions include:

- Does the configured scope persist after one transmission?
- Is there a firmware-level default scope?
- Is scope automatically reset?
- Must the previous scope be explicitly restored?
- Can the current scope be queried?
- What happens after reconnect/reboot?
- How do firmware versions differ?

The Observer must not rely on assumed state behavior.

---

### 4.7 Scope Failure Policy

If a command requires a specific region scope and the Observer cannot safely apply that scope, the default behavior should not silently broaden transmission.

Potential outcomes include:

- Fail the reply.
- Defer/retry the reply.
- Use an explicitly configured fallback scope.
- Permit unscoped fallback only when the operator deliberately enables it.

The exact policy should be determined during implementation planning.

---

### 4.8 Direct Messages and Scope

Region/flood scoping primarily concerns flooded traffic.

Private/direct replies introduced by Scope 3 may not require the same regional flood-scope behavior.

The bot delivery system should therefore distinguish:

- Public flooded response.
- Region-scoped flooded response.
- Direct/private response.

A command's delivery policy should determine which mechanisms apply.

---

### 4.9 Required Research

Before implementation, validate:

- The current OKI Mesh Region Scopes draft.
- The Companion Channel Scoping section and terminology.
- Expected scope identifiers.
- Scope derivation/mapping rules.
- Applicable channels.
- Community fallback expectations.
- Supported MeshCore firmware versions.
- Current Companion Radio Protocol scope commands.
- Current `@liamcottle/meshcore.js` flood-scope support.
- Whether the installed library exposes sufficient high-level APIs.
- Whether additional library support or an upgrade is required.
- Scope persistence behavior.
- Scope restoration behavior.
- Behavior across radio reconnects.
- Interaction between flood scope and normal channel sending.

Any required dependency update remains a protected project boundary and should be reviewed separately.

## 5 Cross-Cutting Requirements

### 5.1 Bot Command Architecture

These features should build on the command-handler boundary established in v2.4.0.

The bot framework should continue separating:

- Command matching.
- Handler execution.
- Handler state.
- Response construction.
- Reply persistence.
- Delivery scheduling.
- Radio transmission.

New routing/delivery features should not require every command handler to reimplement transport mechanics.

---

### 5.2 Response Policy Model

The implementation should evaluate introducing a normalized response/delivery policy associated with a command or generated reply.

Conceptually, policy may eventually describe dimensions such as:

```text
Targeting:
  normal | bot-tag-required

Duplicate response limiting:
  enabled | disabled

Transport:
  channel | private | inherit-request

Flood scope:
  default | region-specific | none

Fallback:
  defined policy
```

The exact configuration model should remain small and explicit.

Do not introduce a generalized rule engine merely to support these four use cases.

---

### 5.3 Configuration

All new configuration must continue to flow through the centralized configuration system.

Configuration should be strictly validated before radio/network side effects occur.

Potential command-level configuration includes:

- Requires bot tag.
- Cooperative response limiting enabled.
- Permitted transport modes.
- Private-response policy.
- Region/flood scope.
- Fallback behavior.

Exact property names should be finalized during implementation planning.

---

### 5.4 Reply Lifecycle

The durable reply model should be extended where necessary to represent intentional delivery outcomes.

Potential states/events include:

- Pending.
- Sent.
- Acknowledged.
- Failed.
- Expired.
- Suppressed because another response satisfied the request.
- Cancelled for another explicit reason.

The exact lifecycle should avoid ambiguous meanings.

An intentionally suppressed response must not be counted as a transmission failure.

---

### 5.5 RF / Mesh Safety

The principal design constraint of this pillar is reducing unnecessary RF use.

Requirements include:

- Do not transmit a targeted command response from bots that were not addressed.
- Suppress redundant queued replies where the command explicitly permits it.
- Prefer private/direct delivery where a private interaction and valid route support it.
- Respect configured region scope for flooded responses.
- Do not silently broaden scoped traffic.
- Reuse existing airtime coordination.
- Avoid aggressive direct-message retries.
- Avoid retry storms when ACKs are missing.
- Do not let region-scope manipulation race across queued transmissions.
- Preserve bot reply prioritization and quiet-air behavior.

---

### 5.6 Compatibility

Existing v2.4.0 bot configurations should remain valid unless an explicitly approved migration is required.

Existing commands should continue working without enabling the new capabilities.

New behavior should be opt-in where it changes transmission semantics.

---

### 5.7 Security & Trust Boundaries

Inbound channel messages, private messages, Companion identities, and scope-related data must be treated as untrusted protocol input.

Requirements include:

- Validate all structured inputs.
- Bound message lengths.
- Preserve UTF-8 safety.
- Do not construct unsafe dynamic regular expressions from arbitrary Companion names without escaping.
- Do not allow crafted bot tags to bypass command matching.
- Do not allow malformed private messages to corrupt durable handler state.
- Validate configured region identifiers.
- Avoid logging unnecessary private-message content.
- Never expose sensitive private-message metadata beyond approved reporting requirements.

---

### 5.8 Metrics & Observability

Where practical, bot telemetry should distinguish new delivery behaviors.

Potential metrics include:

- Tagged commands received.
- Tagged commands matched.
- Tagged commands ignored because another bot was addressed.
- Replies suppressed due to another satisfactory response.
- Private commands received.
- Private replies attempted.
- Private replies acknowledged.
- Private replies timed out.
- Private replies failed.
- Scoped replies attempted.
- Scoped replies sent.
- Scope-application failures.
- Explicit fallback usage.

These metrics should support operational understanding without creating unnecessary high-cardinality storage.

---

### 5.9 Interaction With Pillar 1

Enhanced Bots may consume data introduced by Improved Telemetry & Reporting, but ownership should remain clear.

Pillar 1 owns observation/persistence of reusable topology information.

Pillar 3 owns bot-response policy and delivery behavior.

For example:

```text
Pillar 1:
What paths have we observed for this node?

Pillar 3:
Is any of that information safe and appropriate to use when delivering this private bot reply?
```

Bot delivery must not assume that every path observation is automatically routable.

## 6 Acceptance Criteria

This pillar is complete when the approved child features collectively satisfy the following.

### 6.1 Targeted Bot Commands

- A command can be configured to require explicit bot targeting.
- The running bot obtains the appropriate Companion identity from the connected device where supported.
- A message such as:

```text
@[🤖Jeymz.011.OBV_BOT] !echo
```

is processed only by the Observer whose Companion identity matches the supplied tag.

- Another bot supporting the same `!echo` command does not respond.
- Companion names containing emoji and other Unicode characters are correctly supported.
- Untagged commands continue functioning where configured.
- A renamed Companion does not require manually changing every tagged command definition if runtime identity is available.
- Malformed tags fail safely.

### 6.2 Cooperative Response Limiting

- Response limiting can be enabled independently for selected commands.
- Commands without the option retain existing behavior.
- A pending reply can be suppressed after another satisfactory response is observed.
- Unrelated messages do not suppress a pending reply.
- Handler-appropriate evidence is used to determine whether the original request was satisfied.
- Replies already transmitting are not cancelled.
- Suppression is persisted/reported distinctly from failure and expiration.
- Existing reply queue durability remains intact.

### 6.3 Private Bot Conversations

- Supported bot commands can be recognized from MeshCore private/contact messages where supported by the protocol/library.
- Existing command handlers can be reused for private requests where appropriate.
- Private requests can receive private responses.
- Direct routes use validated route/contact behavior rather than blindly reversing arbitrary observed packet paths.
- ACK-capable sends track acknowledgement state.
- Missing ACKs are distinguishable from explicit send failures.
- ACKs are not represented as human read receipts.
- A direct-send failure does not automatically create an unscoped public flood unless explicitly configured.
- Retry behavior is bounded and RF-safe.

### 6.4 Region-Scoped Responses

- A bot command can declare the intended response region/scope using the approved configuration model.
- Region configuration is validated before runtime.
- Applicable region names are resolved according to the supported MeshCore/OKI Mesh scoping model.
- Scoped transmission is serialized with associated channel transmission when required by Companion state behavior.
- Concurrent bots cannot accidentally exchange scopes.
- Scope-application failures are observable.
- A configured scoped reply does not silently fall back to unrestricted flooding.
- Scope state is restored or otherwise safely managed according to validated protocol behavior.
- Direct/private replies are not unnecessarily subjected to flooded-channel region policy.

### 6.5 RF Efficiency

- Targeted bot invocation reduces responses from unintended bots.
- Cooperative suppression reduces redundant queued replies.
- Private bot interactions can avoid public channel floods where supported.
- Region-scoped responses remain within their configured routing policy.
- New functionality does not bypass existing airtime coordination.
- Operational testing shows no reply storms, scope races, or runaway retries.

### 6.6 Quality

- All new bot configuration is centrally parsed and strictly validated.
- Existing v2.4.0 bot configurations remain supported where practical.
- Unicode bot-tag behavior is tested.
- Cooperative response correlation is tested against false-positive suppression.
- Private-message delivery and ACK lifecycle are tested.
- Scope-setting/transmission serialization is tested.
- Radio reconnect scenarios are tested.
- Durable reply migration/state handling is tested.
- Full test and lint workflows pass.
- Operator documentation explains targeting, suppression, private messaging, ACK semantics, region scopes, fallback policies, and RF implications.

## 8 Open Questions

These should be resolved during feature planning rather than guessed during implementation.

### 8.1 Bot Tagging

- What exact user-facing syntax should identify a bot?

## 9 Release Intent

This pillar should make MeshCore Observer bots substantially better mesh citizens by improving four parts of bot communication.

### 9.1 Am I responding to the right request?

Users should be able to explicitly target a particular Observer bot when they do not want every compatible bot on the channel to answer.

A bot should understand:

```text
@[This Bot] !command
```

as fundamentally different from:

```text
!command
```

when the command is configured for explicit targeting.

### 9.2 Is my response still necessary?

A bot should be capable of recognizing when another participant has already satisfactorily answered selected requests.

If its own response is still waiting in the queue, it should be able to stay silent rather than transmitting redundant information.

### 9.3 Does this interaction need to be public?

A user who has established contact with the Observer should be able to use supported bot commands through private messaging.

Where a valid direct route exists, the Observer should respond directly and use available acknowledgement mechanisms rather than unnecessarily flooding the shared channel.

### 9.4 How far should this response travel?

When a bot response does require flooded channel delivery, the Observer should respect the intended Companion Channel Scope / region policy for that command.

A response intended for a local or regional audience should not automatically propagate throughout every reachable portion of the mesh.

Together, these capabilities evolve MeshCore Observer's bots from simple channel command responders into routing-aware participants that make deliberate decisions about:

```text
WHO should respond
        +
WHETHER a response is necessary
        +
HOW the response should be delivered
        +
HOW FAR the response should propagate
```

The guiding principle for this pillar is:

> **MeshCore Observer bots should respond to the right users, only when necessary, using the most appropriate delivery mechanism and the narrowest appropriate routing scope.**

The implementation should achieve this while preserving the stable command-handler architecture, durable reply queue, conservative RF behavior, centralized configuration, and explicit operational semantics established in previous releases.
