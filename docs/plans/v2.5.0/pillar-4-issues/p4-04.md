# [v2.5.0][P4-04] Build shared dashboard and setup control patterns

**GitHub issue:** [#41](https://github.com/Robotti-io/Meshcore-Observer/issues/41)
**Labels:** `release:v2.5.0`, `pillar:ui-ux`, `enhancement`

**Parent epic:** [Pillar 4 — #21](https://github.com/Robotti-io/Meshcore-Observer/issues/21)
**Type:** Feature
**Stage:** Issue scoped; implementation planning pending.

## Outcome and scope

- Provide lightweight shared cards, buttons, inputs, badges/alerts, validation, progress, focus, and dialog/loading conventions.
- Support setup-specific labels/help/error summaries with the same recognizable visual language as the dashboard.
- Keep layout and workflow ownership separate from reusable styling/helpers; retain the existing vanilla frontend.

## Dependencies

- [P4-02 — #39](https://github.com/Robotti-io/Meshcore-Observer/issues/39)
- [P4-03 — #40](https://github.com/Robotti-io/Meshcore-Observer/issues/40)

Dependencies identify required evidence/interfaces for implementation. They do not require finishing an entire consuming/owning epic before independent planning. Existing shared services retain their owning issue.

## Acceptance criteria

- [ ] Controls have explicit labels, keyboard/focus states, validation/help treatment, and consistent disabled/dangerous states.
- [ ] Setup and reporting consumers can reuse the patterns without importing each other's service workflows.
- [ ] Useful helper behavior has tests; static CSS is verified visually without implementation-mirroring tests.

## Validation expectations

Meaningful helper/interaction tests and populated keyboard/responsive review; npm test and npm run lint for implementation.

## Existing seams and approval boundaries

Existing client CSS/JS/page seams and shared static resources.

Follow AGENTS.md: JavaScript ES modules, centralized strict AJV/configuration/logging, existing seams, and always-on MetricsStore ownership. Concrete authentication, storage, public API/MQTT, dependency, logging-contract, CSP, and deployment changes require explicit approval in the implementation plan. Real hardware, service, privilege, restart, or network operations require the applicable authorization; issue capture performs none.
