# [v2.5.0][P3-06] Suppress redundant pending replies using handler-aware response evidence

**GitHub issue:** [#57](https://github.com/Robotti-io/Meshcore-Observer/issues/57)
**Labels:** `release:v2.5.0`, `pillar:enhanced-bots`, `enhancement`, `configuration`

**Parent epic:** [Pillar 3 — #20](https://github.com/Robotti-io/Meshcore-Observer/issues/20)
**Type:** Feature
**Stage:** Issue scoped; implementation planning pending.

## Outcome and scope

- Add command-opt-in satisfactory-response recognition using request/sender/trigger/time/state evidence.
- Coordinate pending cancellation with the actual transmission-commit boundary and persist a distinct suppressed outcome.
- Keep unrelated messages, generic mentions, and commands needing multiple replies from triggering suppression.

## Dependencies

- [P3-02 — #53](https://github.com/Robotti-io/Meshcore-Observer/issues/53)
- [P3-05 — #56](https://github.com/Robotti-io/Meshcore-Observer/issues/56)

Dependencies identify required evidence/interfaces for implementation. They do not require finishing an entire consuming/owning epic before independent planning. Existing shared services retain their owning issue.

## Acceptance criteria

- [ ] A valid competing answer can suppress only an eligible uncommitted reply.
- [ ] False-positive, overlapping-request, duplicate/late response, and dispatch-race cases preserve intended delivery.
- [ ] Suppression survives restart/reporting distinctly from sent, failed, expired, or administrative cancellation.

## Validation expectations

Deterministic multi-bot/correlation/commit race and lifecycle tests; npm test and npm run lint.

## Existing seams and approval boundaries

Handlers, inbound message pipeline, ReplyQueue, MetricsStore.

Follow AGENTS.md: JavaScript ES modules, centralized strict AJV/configuration/logging, existing seams, and always-on MetricsStore ownership. Concrete authentication, storage, public API/MQTT, dependency, logging-contract, CSP, and deployment changes require explicit approval in the implementation plan. Real hardware, service, privilege, restart, or network operations require the applicable authorization; issue capture performs none.
