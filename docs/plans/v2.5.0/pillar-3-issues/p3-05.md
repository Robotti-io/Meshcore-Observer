# [v2.5.0][P3-05] Persist reply delivery policy and extended lifecycle state

**GitHub issue:** [#56](https://github.com/Robotti-io/Meshcore-Observer/issues/56)
**Labels:** `release:v2.5.0`, `pillar:enhanced-bots`, `enhancement`

**Parent epic:** [Pillar 3 — #20](https://github.com/Robotti-io/Meshcore-Observer/issues/20)
**Type:** Feature
**Stage:** Issue scoped; implementation planning pending.

## Outcome and scope

- Extend durable reply context to represent approved targeting/transport/scope/fallback policy and lifecycle evidence.
- Preserve versioned handler state and existing queue/migration ownership; define recovery of older pending replies and configuration changes.
- Represent suppression, transmission, ACK, timeout/failure evidence without conflating meanings or counting a delivery twice.

## Dependencies

- [P3-02 — #53](https://github.com/Robotti-io/Meshcore-Observer/issues/53)

Dependencies identify required evidence/interfaces for implementation. They do not require finishing an entire consuming/owning epic before independent planning. Existing shared services retain their owning issue.

## Acceptance criteria

- [ ] Policy and required context survive restart with explicitly compatible legacy defaults.
- [ ] Transactional migrations preserve IDs, handler state, pending/history rows, and existing datasets.
- [ ] Lifecycle transitions have an explicit commit boundary and distinct terminal/ACK semantics, with strict input validation.

## Validation expectations

Migration/reopen/legacy/context and state-transition fixtures; npm test and npm run lint.

## Existing seams and approval boundaries

MetricsStore, reply queue/dispatcher, versioned handler state.

Follow AGENTS.md: JavaScript ES modules, centralized strict AJV/configuration/logging, existing seams, and always-on MetricsStore ownership. Concrete authentication, storage, public API/MQTT, dependency, logging-contract, CSP, and deployment changes require explicit approval in the implementation plan. Real hardware, service, privilege, restart, or network operations require the applicable authorization; issue capture performs none.
